# /write-issue — 히어링으로 구체화한 이슈 등록

목표: **그 이슈만 읽고 새 세션이 작업을 시작할 수 있는 이슈**를 만든다. 이 리포의 세션은
이슈 하나를 입력으로 시작하므로(CLAUDE.md Task management: 작업 단위 = 이슈 1개), 이슈가
자급자족이 아니면 다음 세션이 맥락 재발굴부터 하게 된다 — 그 비용을 지금 히어링으로 지불한다.

이 스킬은 **형식 통일**이지 형식 확장이 아니다. CLAUDE.md가 금지하는 라벨·이슈 템플릿·
마일스톤은 도입하지 않는다. 단 **Projects 보드 "aws-reps 로드맵"(프로젝트 #1)은 예외가
아니라 의무다** — 등록한 이슈는 보드에도 추가한다 (§3. 등록 절차 참조).

## 1. 맥락 수집 — 묻기 전에 대화와 리포에서 찾는다

히어링 항목은 아래 6개다. **대화·리포·기존 이슈에서 이미 답을 알 수 있는 항목은 묻지
않는다** — 기계적 전체 설문은 사용자 시간 낭비이고, 이 스킬의 요점은 "빈 곳만" 채우는 것이다.

| # | 항목 | 답이 채워야 하는 것 |
|---|------|--------------------|
| 1 | 동기 | 왜 지금 이 작업인가, 어떤 문제/불편을 푸는가 |
| 2 | 완료 판정 | 무엇을 보면 "끝났다"고 확인하나 — 검증기·테스트·프리뷰·실기기 중 해당하는 것 |
| 3 | 자산 위치 | 작업에 필요한 파일 경로·외부 리포·문서·스키마 (새 세션이 탐색 없이 찾도록) |
| 4 | 범위 제외 | 인접해 있어서 같이 하고 싶어질 텐데 명시적으로 안 하는 것 |
| 5 | 선행 조건 | 먼저 끝나야 하는 이슈/결정 + **그 이유** (이유 없는 의존은 나중에 무시된다) |
| 6 | 열린 결정 | 아직 안 정해진 선택지 — 사용자에게 물어서 정하는 것이 기본 |

빈 곳을 채울 때 **사실과 결정을 구분한다**:

- **사실**(자산 위치, 현재 코드 상태, 선행 이슈 존재 여부)은 리포·대화를 조사해 스스로
  채운다 — 조사로 알 수 있는 것을 사용자에게 묻는 건 시간 낭비다.
- **결정**(완료 범위, UX 선택, 분할 단위, 우선순위 같은 선택지)은 조사로 채울 수 없다.
  **추정이나 "권장안"으로 조용히 메우지 말고 적극적으로 사용자에게 질문한다** — 이슈는
  다음 세션의 작업 지시서라서, 여기서 어물쩍 넘긴 결정은 작업 중간에 사용자를 다시
  불러오거나 틀린 방향의 재작업이 된다. 지금 묻는 게 가장 싸다.

질문은 **한 번에 몰아서** 하고(2~4개 목표), 각 질문에 **구체적 선택지와 권장안을 붙여**
사용자가 한마디로 답할 수 있게 한다 (AskUserQuestion 도구가 있으면 그걸 쓴다). 사용자가
"그건 작업하면서 정하자"고 답한 항목만 "권장 경로 + 대안 채택 시 보고" 형태로 완료 기준에
위임을 명시한다. 사실까지 다 채워졌고 결정거리가 없을 때만 질문 없이 초안으로 간다.

히어링 중 작업이 둘 이상으로 드러나면 이슈를 쪼갠다 — 작업 단위 = 이슈 1개.

## 2. 초안 작성 — 표준 형식

````markdown
제목: <type>: <한 줄 요약>        ← type은 커밋 컨벤션과 동일: feat/fix/docs/chore/content

## 배경
왜 + 현재 상태 + 자산 위치(경로·리포·스키마). 새 세션이 이것만 읽고 착수할 수 있게.

## 완료 기준
- [ ] 검증 가능한 결과 단위로 쓴다 ("~를 개선"처럼 판정 불가한 문구 금지)
- [ ] 열린 결정은 "권장 경로 + 불가하면 보고 후 결정" 형태로 체크박스에 명시
- [ ] 마지막 체크박스 = 검증 방법 (해당하는 것: 검증기 통과 / 프리뷰 배포 확인 / 실기기(폰) 확인)
- [ ] 하네스(CLAUDE.md·.claude/·scripts/) 변경이 포함되면: PR 착지 + develop→main 전파

## 범위 제외          ← 4번 답이 있을 때만. 없으면 섹션 생략
## 선행 조건          ← 5번 답이 있을 때만. "#N 완료 후 — <이유>" 형태
````

섹션은 이 네 개가 전부다. 배경 없는 이슈(왜 하는지 모름), 완료 기준 없는 이슈(끝을 모름)는
등록하지 않는다. 범위 제외·선행 조건은 해당할 때만 — 빈 섹션을 형식적으로 채우지 않는다.

본문에서 다른 이슈는 `#N`으로 참조한다. 이 이슈를 닫을 커밋/PR이 `closes #N`을 쓸 수 있게
완료 기준은 한 PR 단위로 수렴시킨다.

## 3. 확인 → 등록

1. 완성된 제목+본문을 사용자에게 그대로 보여주고 확인받는다. **확인 없이 바로 등록 금지**
   — 히어링 답을 잘못 해석했을 수 있고, 등록 후 수정은 웹을 오가야 한다.
   예외: 작업 중 발견한 파생 과제를 자율 세션에서 등록할 때는 초안 확인을 생략하되,
   세션 보고에 등록한 이슈 링크와 본문 요지를 반드시 포함한다.
2. 등록:
   - gh 허용 머신: `gh issue create --title "<제목>" --body "<본문>"`
   - gh 차단 머신(git_guard가 gh를 막는 회사 머신 등): 완성 본문을 코드블록으로 출력하고
     GitHub 웹에서 등록하도록 안내한다. 등록을 미루지 말 것 — 본문 출력까지가 이 스킬의 몫.
3. 보드 추가 — 등록 직후, 이슈를 Projects 보드 "aws-reps 로드맵"에 넣는다 (CLAUDE.md
   Task management: 보드는 큐의 시각화, 갱신은 세션의 몫). `/land`만 기다리면 이슈만
   등록하고 끝나는 세션에서 이슈가 보드 밖에 남는다 — 등록한 세션이 바로 추가한다.
   - gh 허용 머신: `gh project item-add 1 --owner "@me" --url <이슈 URL>` 후 **Phase
     필드를 설정**한다 (Milestones 대신 Phase 필드 — 필드 설정 스크립트는 land 스킬
     "보드 갱신" 참조).
   - gh 차단 머신: 생략하고 보고에 "보드 미갱신"을 명시한다 — 다음 gh 가능 세션이 동기화한다.

## 좋은 예 / 나쁜 예

- 좋은 배경 (#6): "별도 프로젝트 `~/pdk/projects/aws-cloud-drills`에 검증된 퀴즈 데이터
  150문항이 있다 (`data/questions/*.json`, 스키마는 `types/quiz.ts`)" — 경로·스키마까지
  줘서 다음 세션이 탐색 없이 착수했다.
- 좋은 선행 조건 (#8): "#7 완료 후 시작 (섹션 구조 확정 전에 본문을 고치면 재작업 발생)"
  — 이유가 있어서 순서가 지켜진다.
- 나쁜 완료 기준: "- [ ] 퀴즈 UI 개선" — 무엇을 보면 끝인지 판정 불가. →
  "- [ ] 채점 후 선택지별 해설 표시 (복수정답 포함), 프리뷰에서 확인"처럼 결과 단위로.
