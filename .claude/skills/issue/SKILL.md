# /issue — 이슈 대응 표준 절차

입력: 이슈 번호 1개 (없이 호출되면 보드 큐 맨 앞의 Todo 이슈를 제안하고 확인받는다).
5단계를 한 세션 안에서 순서대로 실행한다. 단계를 건너뛰지 않는다 — 특히 4(검증).

## 0. 착수

1. `git fetch origin` — develop이 origin/develop과 일치하는지 확인 (다른 PC 작업 가능성).
2. 이슈를 읽는다: `gh issue view <N>` (+ 부모/하위: `--json`으로 subIssues·parent 확인).
   gh 차단 머신이면 사용자에게 이슈 본문 붙여넣기를 요청한다.
3. **선행 조건 확인**: 본문의 선행 이슈가 열려 있으면 멈추고 보고한다 (이유 무시 금지).
4. WIP 1 확인: 보드에 In Progress가 이미 있으면 사용자에게 알리고 진행 여부를 묻는다.
5. 보드에서 이 이슈를 **In Progress**로 (절차는 land 스킬 "보드 갱신" — TARGET만 다름).
6. 작업 브랜치 분기: `git switch -c <type>/<주제> develop`.

## 1. 파악

이슈 본문(배경·완료 기준·범위 제외)과 언급된 자산 경로를 실제로 열어 확인한다.
본문과 리포 현실이 어긋나면 (파일이 없다, 이미 됐다) 멈추고 보고한다.

## 2. 요건 정리

완료 기준 체크박스를 작업 목록으로 변환한다 (TaskCreate 사용 가능).
- 체크박스가 판정 불가능하거나 열린 결정이 숨어 있으면 **추측하지 말고 사용자에게 질문**한다.
- 이슈가 커서 여러 작업 단위로 드러나면 /write-issue로 분할부터 한다 (작업 단위 = 이슈 1개).

## 3. 실장

- **spike 이슈**: 산출물은 코드가 아니라 결정. 타임박스 내에서 조사하고, 결과를 spike
  이슈 본문/코멘트에 기록한다. 결정에 따라 구현 이슈(`task` 라벨)를 /write-issue로 만들어
  부모 에픽의 sub-issue로 연결(GraphQL `addSubIssue`)하고 보드에 추가(Phase=부모)한다.
  버려도 되는 실험 코드는 커밋하지 않는다.
- **task/content/chore 이슈**: 구현한다. 커밋은 conventional-commits 영어.

## 4. 검증 — 생략 불가 게이트

- 코드 변경: `npm run validate` 통과 + 프리뷰(Vercel 브랜치 프리뷰 또는 로컬)에서 실동작 확인.
- UI 변경: 실기기(폰) 확인이 완료 기준에 있으면 사용자에게 프리뷰 URL을 주고 확인을 받는다.
- spike: 결정 요지를 사용자에게 보여주고 승인받는다.
- 검증 실패 상태로 5단계로 넘어가지 않는다. 실패를 그대로 보고한다.

## 5. 착지

/land 스킬을 호출한다 (경로 판단·머지·보드 Done·`closes #N` 자동 닫힘·**이슈 체크박스 close-out** 포함 — 2단계에서 만든 작업 목록이 완료 기준 체크박스와 대응하므로, 달성분을 land 스킬 "이슈 close-out" 절차로 `[x]` 갱신한다).
착지 후 이 이슈에서 파생됐지만 하지 않은 일이 있으면 /write-issue로 등록한다 (발견 즉시 이슈).
