AWS Certified Developer – Associate (DVA-C02)

0단계 — AWS의 문법

어떤 서비스를 배우든 계속 등장하는 기반 개념 4가지. 여기서 말하는 "문법"은 이후 모든 서비스 설명이 전제로 깔고 가는 공통 언어입니다. 이 문서는 개념 이해 중심이며, 실습은 포함하지 않습니다.

빈출빈도: ★★★ 매우 자주 (직접 문항 다수) ★★☆ 보통 (전제 지식으로 계속 등장) ★☆☆ 낮음 (직접 출제 드묾)
01

리전 / 가용영역(AZ)

"내 리소스는 물리적으로 어디에 있는가"
빈출 ★★☆ · 직접 문항은 적지만 모든 문제의 전제

AWS는 전 세계에 데이터센터를 깔아 두고, 이를 리전(Region) → 가용영역(AZ) → 데이터센터의 계층으로 묶어서 제공합니다.

계층 구조: 리전 ⊃ 가용영역(AZ) ⊃ 데이터센터. 엣지 로케이션은 이와 별개의 촘촘한 캐시 거점망.

핵심 개념

용어정의기억할 것
리전 (Region)지리적으로 독립된 지역. 예: 서울 ap-northeast-2리전을 선택하면 대부분의 리소스는 그 리전 안에만 존재. 기준: 지연시간, 규제(데이터 주권), 서비스 지원 여부, 가격
가용영역 (AZ)리전 내 물리적으로 분리된 데이터센터 그룹 (리전당 보통 3개 이상)한 AZ가 정전·재해로 죽어도 다른 AZ는 살아있음 → Multi-AZ = 고가용성(HA)의 기본기
엣지 로케이션전 세계 수백 개의 캐시/접점 거점CloudFront, Route 53, Global Accelerator가 사용. 리전·AZ와는 별개

서비스의 "범위" 감각

  • 글로벌 서비스: IAM, Route 53, CloudFront — 리전을 골라도 전체에 적용
  • 리전 서비스: S3, DynamoDB, Lambda — 리전 단위로 존재 (대부분이 여기 해당)
  • AZ 단위 리소스: EC2 인스턴스, EBS 볼륨, 서브넷 — 특정 AZ 하나에 놓임

EBS 볼륨은 같은 AZ의 EC2에만 붙일 수 있다 — 이런 식으로 "이 리소스는 어느 범위에 사는가"가 뒤 단계의 함정 문제로 계속 재활용됩니다.

EXAM POINT — DVA 시험에서는
  • "리전이 무엇인가" 같은 직접 질문은 드물고, 고가용성을 위해 여러 AZ에 배포하라는 선택지의 전제로 등장
  • 지연시간을 줄여야 한다 → 사용자와 가까운 리전 선택 또는 CloudFront(엣지)가 정답 패턴
  • 리소스 이름 규칙 감각: 리전 코드 ap-northeast-2, AZ 코드 ap-northeast-2a
02

IAM 기초

"누가(Who) 무엇을(What) 할 수 있는가(Can do)"
빈출 ★★★ · DVA 최다 빈출 주제 중 하나

IAM(Identity and Access Management)은 AWS의 출입 통제 시스템입니다. 모든 API 호출은 실행 전에 "이 주체가 이 행동을 이 리소스에 해도 되는가?"를 IAM에게 검사받습니다. 구성 요소는 딱 두 종류로 나눠서 보면 쉽습니다: 주체(Identity)와 권한(Policy).

주체(유저·그룹·롤)에 정책(JSON)을 연결하면, 그 주체가 리소스에 접근할 수 있게 된다.

4가지 구성 요소

요소무엇인가한 줄 비유
유저 (User)사람이나 애플리케이션을 나타내는 영구 신원. 비밀번호(콘솔용)와 액세스 키(API용)를 가질 수 있음사원증을 가진 직원
그룹 (Group)유저의 묶음. 그룹에 정책을 붙이면 소속 유저 전원에게 적용"개발팀" 부서
롤 (Role)고정 자격증명이 없는, 필요할 때 빌려 쓰는 신원. EC2·Lambda 같은 서비스나 다른 계정의 유저가 맡을(assume) 수 있고, 맡는 순간 임시 자격증명이 발급됨방문증 — 아무나 발급받을 수 있게 정해둔 규칙에 따라 잠깐 빌려 쓰고 반납
정책 (Policy)권한을 정의하는 JSON 문서. 주체(유저/그룹/롤)에 연결해야 효력 발생출입 허가 목록

정책 JSON의 3대 키워드

  • Effect — Allow 또는 Deny. 기본은 전부 거부(암묵적 Deny)이고, 명시적 Deny는 어떤 Allow보다 항상 이긴다
  • Action — 허용/거부할 API 동작. 예: s3:GetObject, dynamodb:PutItem
  • Resource — 대상 리소스의 ARN. 예: arn:aws:s3:::my-bucket/*

평가 순서 감각: 명시적 Deny 있으면 → 거부 / 없고 Allow 있으면 → 허용 / 둘 다 없으면 → 거부(기본값).

왜 "유저의 액세스 키"가 아니라 "롤"인가

EC2 인스턴스 안의 코드가 S3에 접근해야 한다면? 액세스 키를 코드나 서버에 박아두면 유출 시 영구적으로 악용됩니다. 대신 인스턴스에 롤을 부여하면 SDK가 임시 자격증명을 자동으로 받아와 사용하고, 자격증명은 몇 시간 단위로 자동 만료·갱신됩니다. "AWS 위에서 도는 코드에는 키 대신 롤" — 이 한 문장이 DVA 전체를 관통하는 정답 패턴입니다.

EXAM POINT — DVA 시험에서는
  • "EC2/Lambda/ECS에서 다른 AWS 서비스에 접근" → 정답은 거의 항상 IAM 롤. 액세스 키를 코드/환경변수/AMI에 넣는 선택지는 오답
  • 최소 권한 원칙(Least Privilege): * 전체 허용보다 필요한 Action·Resource만 허용하는 선택지가 정답
  • 정책 JSON을 보여주고 "이 요청은 허용되는가?"를 묻는 문제 — Deny 우선 규칙과 Resource ARN 매칭을 읽을 줄 알아야 함
  • 교차 계정 접근, 임시 권한 → STS AssumeRole 키워드
  • 루트 계정은 일상 업무에 쓰지 않고 MFA로 잠가둔다 — 베스트 프랙티스형 문항
03

AWS API의 구조

콘솔·CLI·SDK는 전부 "같은 API"를 부르는 다른 껍데기
빈출 ★★★ · 자격증명 관련은 개발자 시험의 핵심

AWS의 모든 것은 HTTPS API입니다. 웹 콘솔에서 버튼을 누르든, 터미널에서 CLI 명령을 치든, 코드에서 SDK를 호출하든 — 최종적으로는 전부 동일한 API 엔드포인트로 서명된 HTTP 요청이 날아갑니다. 이 사실 하나를 알면 "콘솔에서 되는 건 코드에서도 된다"는 감각이 생깁니다.

세 가지 도구 모두 같은 API로 수렴한다. 요청마다 자격증명으로 서명(SigV4)되고, IAM이 인가를 검사한다.

자격증명(Credentials)이란

종류구성용도 / 특징
비밀번호ID + 비밀번호 (+ MFA)콘솔 로그인 전용. API 호출에는 못 씀
액세스 키Access Key ID + Secret Access Key 한 쌍CLI·SDK에서 API 호출용. 영구 자격증명이라 유출 시 치명적 — 절대 코드/깃허브에 넣지 않기
임시 자격증명키 쌍 + 세션 토큰 (STS 발급)롤을 맡으면 자동 발급. 만료 시간이 있어 안전 → 권장 방식

SDK/CLI가 자격증명을 찾는 순서 (Credential Provider Chain)

코드에 키를 직접 쓰지 않아도 SDK가 알아서 아래 순서로 자격증명을 탐색합니다:

  • ① 코드에 명시된 파라미터 → ② 환경변수 (AWS_ACCESS_KEY_ID 등) → ③ 설정 파일 (~/.aws/credentials) → ④ 붙어 있는 IAM 롤 (EC2 인스턴스 프로파일, Lambda 실행 롤 등)

그래서 EC2에 롤만 붙여두면 코드는 자격증명을 전혀 몰라도 동작합니다. "같은 코드가 로컬에서는 설정 파일, EC2에서는 롤로 인증된다" — 이 체인 개념이 시험에 나옵니다.

EXAM POINT — DVA 시험에서는
  • "애플리케이션에 자격증명을 가장 안전하게 제공하는 방법은?" → IAM 롤 (하드코딩·환경변수·설정파일 배포는 오답)
  • API 요청은 SigV4로 서명된다 — S3 presigned URL 등 뒤 단계 주제의 기반
  • CLI에서 임시로 다른 권한이 필요 → sts assume-role 패턴
  • 403 에러 = 인증은 됐지만 인가(정책) 실패, 401/서명 오류 = 자격증명 문제 — 트러블슈팅형 문항의 단서
04

요금의 기본 사고방식

쓴 만큼 낸다 · 관리형 vs 직접 운영
빈출 ★☆☆ · 직접 출제는 드물지만 "정답 고르는 감각"의 뿌리

AWS 요금의 대원칙은 종량제(Pay-as-you-go) — 선투자 없이, 쓴 만큼만, 초·요청·GB 단위로 냅니다. 과금 축은 크게 세 가지입니다: 컴퓨팅(실행 시간), 스토리지(저장 용량×기간), 데이터 전송(특히 AWS 밖으로 나가는 아웃바운드). 들어오는 데이터(인바운드)는 대부분 무료라는 것도 기억해 두세요.

오른쪽으로 갈수록 운영 부담이 AWS로 넘어가고, 과금은 "확보한 자원" 기준에서 "실제 사용량" 기준으로 바뀐다.

관리형(Managed) vs 직접 운영의 의미

관리형 서비스란 서버 프로비저닝·패치·백업·장애 조치 같은 "운영 잡일"을 AWS가 대신 해주는 서비스입니다. DVA는 개발자 시험이라 "운영 부담을 줄이고 코드에 집중"이라는 방향의 선택지가 정답인 경우가 압도적으로 많습니다. 문제에서 "minimal operational overhead", "least management effort" 같은 문구가 보이면 관리형/서버리스 쪽 선택지에 가중치를 두세요.

알아두면 좋은 부가 개념

  • 프리 티어 — 신규 계정에 일부 서비스를 일정량 무료 제공 (학습용)
  • EC2 구매 옵션 감각 — 온디맨드(기본, 유연) / 예약·Savings Plans(장기 약정 할인) / 스팟(최대 90% 할인, 대신 중단될 수 있음 → 중단 허용 워크로드용)
  • 리전마다 가격이 다르다 — 같은 서비스라도 리전에 따라 단가 차이
  • 공동 책임 모델 — AWS는 "클라우드 자체의" 보안(하드웨어·시설), 고객은 "클라우드 안의" 보안(데이터·IAM 설정·앱)을 책임. 관리형일수록 AWS 쪽 책임 범위가 넓어짐
EXAM POINT — DVA 시험에서는
  • 요금 계산 문제 자체는 거의 안 나옴 (그건 Cloud Practitioner 영역)
  • 대신 "운영 오버헤드 최소화" = 관리형/서버리스 선택이라는 판단 기준으로 계속 활용됨
  • "비용 효율적(cost-effective)" 조건이 붙으면: 안 쓸 때 0원인 서버리스, 중단 허용이면 스팟 — 이런 방향 감각을 묻는 문항

0단계 체크리스트 — 이 문장이 술술 나오면 통과

  • 리전은 지리적 지역, AZ는 리전 안의 분리된 데이터센터 그룹이며, 여러 AZ에 걸치는 것이 고가용성의 기본이다 ★★☆
  • 유저는 영구 신원, 롤은 빌려 쓰는 신원이고, 권한은 정책(JSON: Effect/Action/Resource)을 연결해야 생긴다 ★★★
  • 명시적 Deny는 항상 Allow를 이기고, 기본값은 전부 거부다 ★★★
  • AWS 위에서 도는 코드의 인증은 액세스 키 하드코딩이 아니라 IAM 롤(임시 자격증명)이다 ★★★
  • 콘솔·CLI·SDK는 전부 같은 API를 부르며, 모든 요청은 자격증명으로 서명(SigV4)된다 ★★★
  • SDK는 코드 → 환경변수 → 설정파일 → 롤 순서로 자격증명을 찾는다 ★★☆
  • 요금은 종량제(컴퓨팅·스토리지·아웃바운드 전송)이고, "운영 부담 최소화" 문구는 관리형/서버리스가 정답 방향이다 ★★☆
