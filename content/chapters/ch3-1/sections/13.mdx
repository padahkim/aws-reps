§03에서 User Pool이 붙는 자리는 크게 둘이라고 했습니다. 첫 번째 자리인 API Gateway(§07)는 앱이 이미 받아 온 토큰을 <b>검증</b>했습니다. User Pool이 붙는 두 번째 자리가 <Term id="alb">ALB</Term>입니다. ALB는 토큰을 받는 대신 <b>로그인 자체를 대신 수행</b>합니다 — §08에서 앱이 사용자를 Hosted UI로 보내고 콜백으로 돌아온 코드를 토큰으로 바꾸던 일을, 앱 대신 ALB가 합니다. 그래서 애플리케이션에서 로그인 플로우 코드를 걷어낼 수 있고, 이것을 <b>인증 오프로드</b>라고 부릅니다. 무엇이 어디로 오가는지부터 따라가 봅니다.

⑥에서 백엔드는 로그인 결과를 <b>HTTP 헤더 세 개</b>로 받습니다. 기준이 되는 것은 <Code>x-amzn-oidc-data</Code>입니다 — ALB가 ⑤에서 얻은 클레임을 JWT 형식으로 담고 <b>ALB가 직접 서명</b>(ES256)한 헤더로, ALB가 서명하는 헤더는 이것 하나뿐입니다. 서명한 주체가 User Pool이 아니라 ALB라서, JWT 헤더의 <Code>signer</Code> 필드에 그 ALB의 ARN이 들어 있습니다. 나머지 둘은 하위 호환용으로 남은 <b>ALB 서명이 없는 헤더(legacy unsigned)</b>입니다. <Code>x-amzn-oidc-accesstoken</Code>은 ④에서 받은 Access 토큰 원문이라, Cognito 방식이면 User Pool이 서명한 JWT입니다 — ALB의 서명은 없어도 User Pool의 서명은 §06의 JWKS 방식으로 검증할 수 있습니다(<b>authenticate-oidc</b>라면 그 IdP가 발급한 토큰이므로 검증 가능 여부와 방법도 그 IdP를 따릅니다). <Code>x-amzn-oidc-identity</Code>는 <Code>sub</Code> 값만 평문으로 담은 것이라 어느 쪽의 서명도 없습니다. 그래서 사용자를 식별하고 클레임으로 인가할 때의 기준은 ALB가 서명한 <Code>x-amzn-oidc-data</Code>이고, 그 서명을 검증한 뒤 안의 <Code>sub</Code>를 씁니다. User Pool의 ID 토큰은 백엔드로 넘어오지 않습니다.

<Note>세션 쿠키의 기본 이름은 <Code>AWSELBAuthSessionCookie</Code>이고, 인증 세션의 <b>최대</b> 길이는 <Code>SessionTimeout</Code>이 정합니다 — 기본값 <b>604800초(7일)</b>, 짧게는 1초까지 줄일 수 있습니다. 쿠키 자체에도 7일 만료가 붙지만 문서는 이것을 세션 길이와 <b>별개</b>로 구분합니다. 최대인 이유는 그 전에 끝날 수도 있어서입니다. IdP가 refresh 토큰을 준 경우 ALB는 Access 토큰이 만료될 때마다 IdP에서 갱신(refresh)을 시도하고, 갱신이 실패하면(예: 사용자가 IdP에서 로그아웃한 경우) 타임아웃 전이라도 사용자를 다시 로그인시킵니다.</Note>

이 흐름이 돌아가려면 먼저 갖춰야 할 조건이 있습니다.

<WarnBox>인증 규칙은 <b>HTTPS 리스너에서만</b> 설정할 수 있습니다. HTTP 리스너에는 <Code>authenticate-cognito</Code>·<Code>authenticate-oidc</Code> 액션을 걸 수 없습니다 — 자격 증명이 평문으로 오갈 수 없기 때문입니다.</WarnBox>

붙이는 방식은 둘입니다. <b>authenticate-cognito</b>는 User Pool을 앞세우는 방식으로, User Pool·앱 클라이언트·User Pool 도메인이 필요합니다. ④의 교환은 ALB가 서버 쪽에서 하므로 secret을 안전하게 둘 수 있고, 문서도 앱 클라이언트에 client secret 생성을 요구합니다 — 즉 ALB용 앱 클라이언트는 §03의 <b>confidential client</b>여야 하고, <b>Authorization Code Grant</b>(§08)와 ALB가 요청할 OAuth 스코프를 활성화해 둬야 합니다. 브라우저·모바일 앱용 public client(§03)를 그대로 재사용하지 말고 ALB용 앱 클라이언트를 따로 둡니다.

<Note><b>User Pool은 ALB와 같은 리전에 두는 것이 안전합니다.</b> 같은 리전이어야 한다는 요건은 공식 문서에 없지만, 다른 리전의 User Pool ARN을 넣었더니 <Code>authenticate-cognito</Code> 규칙 생성이 <Code>InvalidLoadBalancerAction</Code>(HTTP 400) 오류로 거부됐다는 보고가 있습니다. 여기서 “보고”는 AWS의 공식 답변이 아니라, 실제로 설정하다 이 오류를 만난 개발자가 공개 이슈 게시판에 남긴 기록이라는 뜻입니다.</Note>

③에서 사용자가 돌아오는 주소가 콜백 URL입니다. Cognito 앱 클라이언트의 콜백 URL에는 <Code>https://&lt;ALB-domain&gt;/oauth2/idpresponse</Code>를 <b>정확히, 모두 소문자로</b> 등록합니다. 외부 연합 IdP가 있다면 그 IdP의 콜백은 ALB가 아니라 <b>Cognito User Pool 도메인</b>을 가리킵니다. <b>authenticate-oidc</b>는 OIDC 호환 IdP에 직접 연결하는 방식이라, Authorization·Token·User Info 엔드포인트와 Client ID·Secret을 손으로 넣고, 그 IdP 쪽에도 리다이렉트 URI로 같은 <Code>https://&lt;ALB-domain&gt;/oauth2/idpresponse</Code>를 등록합니다.

<WarnBox>④·⑤는 ALB가 직접 IdP로 나가는 호출이라, ALB는 IdP의 <b>Token·User Info 엔드포인트에 IPv4로 나갈 수 있어야 합니다.</b> 보안 그룹 아웃바운드와 네트워크 ACL이 이를 허용해야 하며, <b>내부 ALB</b>나 <Code>dualstack-without-public-ipv4</Code>처럼 퍼블릭 IPv4 출구가 없는 구성은 보통 <b>NAT Gateway</b>를 통해 이 경로를 만듭니다.</WarnBox>

보안에서 챙길 것은 둘입니다. 인증은 <b>ALB를 지나는 요청에만</b> 걸리므로, 타깃에 ALB를 거치지 않고 닿는 길이 있으면 인증이 통째로 우회되고 <Code>x-amzn-oidc-*</Code> 헤더도 위조될 수 있습니다. 그래서 타깃 보안 그룹은 <b>ALB 보안 그룹에서 오는 트래픽만</b> 받게 좁힙니다. 그리고 클레임으로 인가하는 백엔드는 <Code>x-amzn-oidc-data</Code>의 <b>서명을 검증하고, JWT 헤더의 <Code>signer</Code>가 예상한 ALB ARN인지</b> 확인한 뒤에 클레임을 씁니다. 로그인 플로우 코드는 ALB가 없애 주지만, 이 검증만은 백엔드 몫입니다.

미인증 요청을 어떻게 다룰지는 <Code>OnUnauthenticatedRequest</Code>가 정합니다.
