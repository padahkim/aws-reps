토큰을 쓰는 두 번째 자리가 <Term id="alb">ALB</Term>입니다. API Gateway가 토큰을 <b>검증</b>했다면, ALB는 한 걸음 더 나아가 <b>로그인 자체를 대신 수행</b>합니다 — 애플리케이션에서 로그인 플로우 코드를 걷어낼 수 있어 <b>인증 오프로드</b>라고 부릅니다. 단, 타깃이 ALB를 거치지 않고도 닿으면 이 인증은 통째로 우회됩니다. 타깃 보안 그룹은 <b>ALB 보안 그룹에서 오는 트래픽만</b> 받게 좁히고, 백엔드는 `x-amzn-oidc-data` 서명을 검증해 JWT 헤더의 <Code>signer</Code>가 예상 ALB ARN인지 확인한 뒤 사용자 클레임을 인가에 사용합니다.

<AlbAuthFlow />

<WarnBox>인증 규칙은 <b>HTTPS 리스너에서만</b> 설정할 수 있습니다. HTTP 리스너에는 <Code>authenticate-cognito</Code>·<Code>authenticate-oidc</Code> 액션을 걸 수 없습니다 — 자격 증명이 평문으로 오갈 수 없기 때문입니다.</WarnBox>

붙이는 방식은 둘입니다. <b>authenticate-cognito</b>는 User Pool을 앞세우는 방식으로, <b>ALB와 같은 리전</b>의 User Pool·앱 클라이언트(§03)·User Pool 도메인이 필요합니다. 여기서 앱 클라이언트는 <b>client secret을 생성한 confidential client</b>여야 하고, <b>Authorization Code Grant</b>와 ALB가 요청할 OAuth 스코프를 활성화해야 합니다. 브라우저·모바일용 public/PKCE 클라이언트(§03·§08)를 그대로 재사용하지 말고 ALB용 앱 클라이언트를 따로 둡니다.

Cognito 앱 클라이언트의 콜백 URL에는 <Code>https://&lt;ALB-domain&gt;/oauth2/idpresponse</Code>를 <b>정확히, 모두 소문자로</b> 등록합니다. 외부 연합 IdP가 있다면 그 IdP의 콜백은 ALB가 아니라 <b>Cognito User Pool 도메인</b>을 가리킵니다. <b>authenticate-oidc</b>는 OIDC 호환 IdP에 직접 연결하는 방식이라, Authorization·Token·User Info 엔드포인트와 Client ID·Secret을 손으로 넣고, 그 IdP 쪽에도 리다이렉트 URI로 같은 <Code>https://&lt;ALB-domain&gt;/oauth2/idpresponse</Code>를 등록합니다.

<WarnBox>ALB는 인증 코드 교환을 위해 IdP의 <b>Token·User Info 엔드포인트에 IPv4로 나갈 수 있어야 합니다.</b> 보안 그룹 아웃바운드와 네트워크 ACL이 이를 허용해야 하며, <b>내부 ALB</b>나 <Code>dualstack-without-public-ipv4</Code>처럼 퍼블릭 IPv4 출구가 없는 구성은 보통 <b>NAT Gateway</b>를 통해 이 경로를 만듭니다.</WarnBox>

미인증 요청을 어떻게 다룰지는 <Code>OnUnauthenticatedRequest</Code>가 정합니다.
