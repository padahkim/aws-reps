User Pool 로그인에는 길이 둘 있습니다. 앱이 로그인 화면을 직접 만들고 SDK로 User Pool 로그인 API를 부르는 길이 하나, Cognito가 호스팅하는 로그인 페이지로 사용자를 보내는 <b>Hosted UI(OAuth)</b> 길이 또 하나입니다. 이 절은 앞의 길을 따라가고, Hosted UI는 §08에서 따로 봅니다. 로그인이 시작해서 끝나기까지 무엇이 오가는지를 다섯 단계로 봅니다. 단계를 눌러 가며 어느 상자와 화살표가 켜지는지 따라가 보세요.

여기서 챙겨야 할 것은 <b>흐름의 방향</b>입니다. 사용자는 User Pool에 자격 증명을 주고, User Pool은 사용자에게 토큰을 줍니다. 백엔드(API Gateway와 그 뒤의 Lambda)는 이 대화에 끼지 않습니다 — 토큰을 받아 검증할 뿐이고, 비밀번호는 구경도 하지 못합니다.

마지막 단계가 말하는 것도 같습니다. 사용자가 구글 계정으로 들어오든 직접 가입한 계정으로 들어오든, <b>앱이 최종적으로 받는 것은 언제나 User Pool이 발급한 토큰</b>입니다. 그래서 앱 코드는 사용자가 어느 경로로 로그인했는지 신경 쓰지 않아도 됩니다.

①단계의 “로그인 요청”에는 방식이 여럿 있고, 이를 <b>인증 흐름(authentication flow)</b>이라 부릅니다. 앱 클라이언트(§03)마다 허용할 흐름을 켜 두고, 앱은 요청에 흐름 이름을 적어 보냅니다.

이 구분이 뒤의 두 곳을 설명합니다. §03의 유출된 자격 증명 탐지는 비밀번호 원문이 와야 유출 목록과 대 볼 수 있어 <Code>USER_PASSWORD_AUTH</Code> 계열만 검사하고 SRP 로그인은 검사하지 못합니다. §09의 User Migration도 같은 이유로, 입력한 비밀번호를 옛 DB에 대 보려면 <Code>USER_PASSWORD_AUTH</Code>나 <Code>ADMIN_USER_PASSWORD_AUTH</Code>로 로그인해야 합니다.
