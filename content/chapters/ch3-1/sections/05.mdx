User Pool 로그인 API로 로그인하면(§04) 토큰이 <b>세 개</b> 나옵니다. Hosted UI(OAuth) 경로는 Grant·scope에 따라 구성이 달라집니다 → §08. 단, 로그인 API로 받은 Access 토큰의 스코프는 자기 정보 조회·수정용인 <Code>aws.cognito.signin.user.admin</Code> 하나뿐입니다 — 리소스 서버의 커스텀 스코프(§07)가 든 Access 토큰은 Hosted UI(OAuth) 경로로 받습니다(Pre Token Generation 트리거로 더하는 방법도 있다, §09). 셋을 “JWT 토큰”으로 뭉뚱그려 외우면 시험에서 갈리는 지점을 놓칩니다 — 용도가 다르고, 수명도 다릅니다.

수명이 이렇게 갈리는 이유는 <b>탈취됐을 때의 피해</b> 때문입니다. ID·Access 토큰은 요청마다 네트워크에 실려 나가므로 새어 나갈 기회가 많고, 그래서 짧습니다. Refresh 토큰은 앱이 안전한 곳에 보관한 채 재발급 때만 쓰므로 노출이 적고, 그래서 길게 둡니다.

<WarnBox>ID·Access 토큰의 유효기간은 <b>Refresh 토큰의 유효기간을 넘길 수 없습니다</b>. Refresh를 60분으로 줄여 놓고 Access를 1일로 두는 설정은 성립하지 않습니다 — 재발급 수단이 먼저 죽는 조합이기 때문입니다.</WarnBox>

<Note>실제 화면에서는 이렇게 나타납니다 — 앱을 일주일 만에 열었는데 로그인 화면이 뜨지 않으면 Refresh 토큰이 살아 있어 조용히 재발급된 것이고, 로그인 화면이 뜨면 Refresh 토큰까지 만료된 것입니다.</Note>
