AWS를 조작하는 도구는 세 가지입니다: 브라우저에서 버튼을 누르는 <b>웹 콘솔</b>, 터미널에서 명령을 치는 <b>CLI</b>, 코드 안에서 호출하는 <b>SDK</b>. 겉모습이 너무 달라서 초심자는 셋을 별개의 시스템으로 착각하기 쉽습니다. 하지만 —

AWS의 모든 것은 **HTTPS API**입니다. 웹 콘솔에서 버튼을 누르든, 터미널에서 CLI 명령을 치든, 코드에서 SDK를 호출하든 — 최종적으로는 전부 동일한 API 엔드포인트로 서명된 HTTP 요청이 날아갑니다. 이 사실 하나를 알면 “콘솔에서 되는 건 코드에서도 된다”는 감각이 생깁니다.

식당에 비유하면 API는 <b>주방</b>이고, 콘솔·CLI·SDK는 홀 주문·전화 주문·배달앱이라는 <b>주문 채널</b>입니다. 어느 채널로 주문하든 요리하는 주방은 하나라서, 메뉴(가능한 작업)도 하나고 주방 규칙(권한 검사)도 하나입니다. 콘솔에서 손으로 하던 일을 스크립트로 자동화할 수 있는 이유, 그리고 권한 설정이 콘솔·CLI·SDK 어디에서든 똑같이 적용되는 이유가 전부 이 구조에서 나옵니다.

<SubTitle>자격 증명(Credentials)이란</SubTitle>

API가 인터넷에 열려 있는 이상, AWS는 날아온 요청이 <b>누구의 것인지</b>를 매번 확인해야 합니다. “나는 이 계정의 이 사용자다”를 증명하는 수단이 자격 증명이고, 요청마다 자격 증명으로 서명을 만들어 붙입니다(이 서명 방식의 이름이 SigV4). 자격 증명은 용도에 따라 세 종류가 있습니다 — 건물 비유로는 각각 <b>정문 출입증</b>(콘솔 로그인용), <b>반납 기한 없는 열쇠</b>(열 수 있는 방은 주인의 권한만큼이지만, 회수하기 전까지 계속 쓸 수 있어 유출에 취약), <b>만료 시각이 찍힌 방문증</b>(임시라 안전)에 해당합니다. 표에 나오는 <b>STS(Security Token Service)</b>는 이 “방문증”, 즉 임시 자격 증명을 발급해 주는 전용 서비스입니다 — 이름 그대로 “보안 토큰을 발급하는 서비스”라고 기억하면 됩니다.

<Note>“액세스 키를 코드에 넣지 말라”가 왜 이렇게 강조될까요? 만료되지 않는 열쇠를 복사해 공개 게시판에 붙여 두는 것과 같기 때문입니다. 피해 범위는 그 키 주인의 권한(IAM 정책)만큼으로 한정되지만, 깃허브에 올라간 키는 봇이 수 분 안에 긁어가고, 권한이 넉넉한 키였다면 채굴용 서버가 수백 대 뜹니다 — 실제로 흔한 사고이고, 시험도 “가장 안전한 방법”을 고르라는 형태로 이 감각을 계속 확인합니다.</Note>

<SubTitle>SDK/CLI가 자격 증명을 찾는 순서 (Credential Provider Chain)</SubTitle>

그럼 키를 코드에 안 넣으면 SDK는 자격 증명을 어디서 얻을까요? 같은 코드가 내 노트북에서도, EC2 서버 위에서도 돌아야 하니 “자격 증명을 두는 곳”은 환경마다 다를 수밖에 없습니다. 그래서 SDK는 정해진 순서로 여러 위치를 차례로 뒤지도록 설계됐습니다 — 이 탐색 순서가 Credential Provider Chain입니다.

코드에 키를 직접 쓰지 않아도 SDK가 알아서 아래 순서로 자격 증명을 탐색합니다:

- ① 코드에 명시된 파라미터 → ② 환경변수 (`AWS_ACCESS_KEY_ID` 등) → ③ 설정 파일 (`~/.aws/credentials`) → ④ <b>붙어 있는 IAM 역할</b> (EC2 인스턴스 프로파일, Lambda 실행 역할 등)

<Note>여기서 <b>역할(Role)</b>이란 고정 자격 증명 없이 필요할 때 “빌려 쓰는” IAM 신원입니다 — 자세한 개념은 <ChLink id="ch0-2">ch0-2 IAM</ChLink>에서 다룹니다. EC2에 역할만 붙여두면 코드는 자격 증명을 전혀 몰라도 동작합니다. “같은 코드가 로컬에서는 설정 파일, EC2에서는 역할로 인증된다” — 이 체인 개념이 시험에 나옵니다.</Note>

순서에도 논리가 있습니다: 명시적인 것(코드 파라미터)이 가장 먼저, 환경에 붙어 있는 것(역할)이 가장 나중 — 즉 <b>구체적인 지정이 기본값을 이깁니다</b>. 그리고 ④번 역할이 “권장 방식”인 이유는 위 표와 연결됩니다: 역할은 만료되는 임시 자격 증명을 자동으로 받아 쓰므로, 유출될 영구 키 자체가 존재하지 않기 때문입니다.
