## 1. 형식별 점수 분포와 우수 형식 후보 (분석 A)

### 1-1. 방법

축2 리포트의 **성분 태그**(`설명·예시·퀴즈·해설` O/X — RUBRIC §7-1)와 축1 리포트의 **항목 점수**(L1~L8)를 **파일 id로 조인**했다. 28파일 전수. 추출은 파일별 독립 에이전트가 두 리포트를 직접 읽어 수행했고, 다음을 **역산 검증**했다:

- 28/28 파일의 `유효 총점`이 L1~L8 항목 점수에서 정확히 재계산됨 (N/A 제외 합 ÷ 2×채점항목수)
- 28/28 파일의 축1 판정이 85%/60% 임계에 정확히 부합
- 축2 판정 분포 **통과 1 / 수정 27 / 재작성 0**, 축1 판정 분포 **통과 24 / 수정 4 / 재구성 0** — 양쪽 `_FINAL_SUMMARY`와 일치
- 항목별 평균 8개 전부 재현 (L1 1.50 · L2 2.00 · L3 1.93 · L4 2.00 · L5 1.89 · L6 1.00 · L7 2.00 · L8 2.00)

→ **추출 오류 0건.** 이 절의 수치는 리포트 원본에서 기계적으로 재현된 값이다. (검증 중 발견된 **published 요약의 부기 불일치 3건**은 §6-2에 별도 보고 — 판정에는 영향 없음.)

### 1-2. 형식 클러스터별 분포

| 형식 클러스터 | 파일 수 | 축1 평균(유효 총점 %) | 총점 분포 | L3 | L4 | L5 | L6 | 순위 판정 |
|---|:--:|:--:|---|:--:|:--:|:--:|:--:|---|
| **설명형 · 실코드 보유**(CLI/JSON/YAML/SDK) | 16 | **86.5%** | 7/8 ×14 · 6/8 ×1 · 5/6 ×1 | 2.00 | 2.00 | 1.88 | 1.00 | **동급** |

교차 분석 — **인터랙티브 보유 여부**: 보유 10파일 86.2% vs 미보유 18파일 85.9%. **차이 0.3%p → 동급.**

### 1-3. 핵심 결론 — **형식별 점수로는 우열을 가릴 수 없다**

프롬프트의 두 안전장치가 **양쪽 다 발동**한다:

1. **표본 3개 미만 → 증거 부족**: 유일하게 점수가 다른 클러스터(퀴즈 보유)가 **N=2**다. 순위에서 제외해야 한다.
2. **평균 1점 이내 → 동급**: 남은 두 클러스터의 차이는 **8점 만점에 0.02점**(86.5% vs 86.2%). 동급이다.

**28파일 중 23파일이 정확히 같은 점수(7/8)**를 받았다. 분산이 사실상 없다.

**왜 그런가 (구조적 이유)**: 축1 루브릭에서 형식을 변별할 수 있는 항목은 L1·L2·L7·L8(인출·해설·난이도·누적복습)인데, **레거시 코퍼스는 퀴즈 성분이 26/28 파일에 없어 이 4개 항목이 전부 N/A**다. 채점되는 4개 항목은 이미 포화 상태다 — L4는 28/28이 만점, L3은 26/28이 만점, L6은 27/27이 1점(분산 0). **루브릭이 형식 차이를 볼 수 있는 눈(L1·L2·L7·L8)이 감겨 있는 상태**에서 나온 점수라, 형식 우열의 증거로 쓸 수 없다.

> **이것이 BOARD 2-1에 주는 의미**: 2-1은 "제안서 §1을 입력으로 형식 팔레트를 확정"하도록 설계돼 있다. 그런데 **§1은 팔레트를 점수로 정할 근거를 주지 못한다.** 이는 평가 실패가 아니라 레거시 코퍼스의 성질이다(퀴즈 결손). → **팔레트는 점수가 아닌 다른 축으로 정해야 한다**(§4 결정 포인트 1에 대안 기준 제시).

### 1-4. 그럼에도 증거가 말하는 것 — 우수 "형식"이 아니라 우수 **패턴** 3가지

점수로 형식을 줄 세울 수는 없지만, 재현된 패턴은 분명하다:

| # | 패턴 | 증거 | 시사점 |
|---|---|---|---|
| **P1** | **개념 직후 예시 인접 → L3=2** | 설명형 26파일 전원 L3=2. 실코드 유무와 무관(실코드 16파일·도식만 10파일 모두 2.00) | **실코드는 L3=2의 필요조건이 아니다.** 도식·비교표·결정표를 개념 직후에 붙이는 것만으로 달성됨 → 팔레트가 "실코드 형식"을 강제할 근거 없음 |
| **P2** | **섹션 원자화 + 용어 첫등장 정의 → L4=2** | **28/28 전원 만점.** 형식·클러스터 불문 | 코퍼스 전체의 확립된 강점. v1이 **깨뜨리지 말아야 할** 것 |
| **P3** | **퀴즈 보유의 L3 역설** | 퀴즈 보유 2파일만 L3=1(평균 1.00 vs 설명형 2.00) | 개념-예시를 퀴즈로 **분리**하면 L3이 떨어진다 → v1 생성 규칙 "예시는 개념 블록 내부 결합"(§3 F-5 #5)의 직접 근거 |

## 3. 규약 v1 초안 (코드 스케치 + Next.js 권고)

> **어조 주의**: 아래는 **초안 제안**이다. 단 `〔A ✅ 확정〕` 표시가 붙은 항목은 **인간이 2026-07-14에 이미 확정**한 것이라(§E-4 7항 + 확정 #8) 재론 대상이 아니며, 여기서는 **v0 대비 델타를 한자리에 보이기 위해** 함께 싣는다. `〔B 미확정〕`은 CONTRACT_PREWORK 권장을 담은 **기술 확정 대기** 항목이다.

### 3-1. 모듈 구조 〔B 미확정 — CONTRACT_PREWORK §2-0/§2-1 권장〕

```
content/chapters/{id}/
  meta.ts    ← chapterMeta + quiz  (순수 데이터, "use client" 금지, 서버 안전)
  body.jsx   ← "use client" + export default 본문 (자유 jsx, 문항 배치는 <Quiz>)
```

**근거 (RSC 제약)**: `"use client"` 모듈의 비컴포넌트 export는 서버 컴포넌트가 import할 수 없다. 그런데 `meta`는 서버 소비가 **필수**다(`generateStaticParams`·내비 목록·`generateMetadata`). v0의 **단일 jsx 파일은 이 제약에 정면으로 걸린다.** 2파일로 쪼개면 서버/클라 경계 = 파일 경계가 되어 제약이 소멸하고, 구조 게이트를 `grep`으로 기계 검사할 수 있다.

**비용**: 파일 2개 관리(표준화 시 기계적 분할). → **v0 구조 변경 제안이다** (§4 결정 포인트 3과 세트).

### 3-2. `chapterMeta` 〔A 확정 + 명명은 B〕

```ts
type ChapterMeta = {
  id: string;                  // "ch1-2". ★안정성 요구 — 개명 시 진도 마이그레이션
  phase: 0|1|2|3|4|5;
  title: string;
  domain: "개발" | "보안" | "배포" | "트러블슈팅";
  examWeight: number;
  prerequisites: string[];     // 〔A ✅ 확정 #4〕 L6 강제의 근거.
                               // 각 개념 블록이 이 중 1개+ 를 본문에서 명시 인용한다(생성 규칙 F-5 #2)
  // chapters?: string[];      // 〔B 미확정〕 복수 챕터 매핑(레거시 1:N — §1-D-4)
};
```

> **`chapters?[]`가 필요한 실증**: 레거시는 챕터와 1:1이 아니다 — `dva-chapter-template`은 **1-2·1-3·1-4 종합**, `stage0`은 **0-1 + 0-2 일부**, `monitoring`은 **5-1·5-2·5-3(+2-3 보너스)**. 단수 `id`만 두면 표준화 때 **강제 분할 또는 허위 매핑**이 강요된다. (§4 결정 포인트 10)

### 3-3. `quiz` — `Question` 〔A ✅ 확정〕

```ts
type Question = {
  id: string;                  // 챕터-로컬 "q1". 전역키는 앱 어댑터가 `${meta.id}:${id}` 합성 (규약 무변경)
  type: "mc";                  // 〔확정 #5〕 v1은 mc만 정식 — 단일·복수정답 모두. recall은 v1.1
  scope: "mini" | "final";     // 인출 시점은 본문 <Quiz> 배치 위치가 표현 (scope 어휘 확장 불요)
  concept: string[];           // 〔확정 #2〕 복수·최소 1. LEARNING_LOOP 숙달/약점 계산이 소비
  scenario: string;
  choices: string[];           // 〔확정 #8〕 길이 가변 — DVA "5개 중 2개 고르기" 대응. 최소 4 권장
  answer: number[];            // 정답 인덱스 배열 — 복수정답 지원
  explanation: string;         // 정답 근거 전용 (v0의 "겸용"에서 의미 축소)
  choiceExplanations: string[];// 〔확정 #1 — 신규모드 의무〕 choices와 1:1 동수.
                               // 선택지별 "왜 틀렸나 + 어떤 상황이면 정답(wouldBeCorrectWhen)"
  fixedChoiceOrder?: boolean;  // 〔확정 #7〕 optional. true면 셔플 금지
};

export const quiz: Question[]; // 〔확정 #3〕 빈 배열 [] 적법. 앱은 빈 quiz에 강건해야 함
```

**v0 대비 순수 신규 필드는 3개뿐**: `type` · `choiceExplanations` · `fixedChoiceOrder?`. 나머지는 기존 필드의 **활용 규칙**(`prerequisites`) 또는 **타입 확장**(`concept` 단수→배열, `choices` 4지 고정→가변).

### 3-4. 본문 문항 배치 API 〔B — CONTRACT_PREWORK §2-5〕

```tsx
<Quiz ids={["q1","q2"]} />   // 챕터-로컬 id 참조 (기본형, grep 가능)
<Quiz scope="final" />       // quiz[].scope 필터 (ids와 상호배타)
```

문항 데이터는 props가 아니라 **ChapterProvider 컨텍스트**에서 조회 → 본문–문항 결합이 문자열 id 참조뿐. 채점·진도·오답노트는 `<Quiz>` 내부(앱 셸 책임).

### 3-5. 본문 네거티브 규정 〔B — CONTRACT_PREWORK §1-D-3〕

본문은 자유 jsx이나 아래를 **금지**한다(앱 셸 침범·오염 방지). **평가가 실증한 필요**다 — `aws-dva-s3-guide`는 사이드바·페이저·전역 `<style>`·`document.getElementById`를 전부 갖춘 **완결 미니 앱**이라 표준화가 "기계 변환이 아니라 절제 수술"(1.5~2h)이 된다:

- ❌ 자체 내비게이션/페이저/사이드바 (내비는 앱 셸 소관)
- ❌ 전역 셀렉터 스타일(`<style>` 내 `table`, `body` 등) — 다른 챕터 오염
- ❌ `document`/`window` 직접 접근·스크롤 제어
- ❌ 외부 리소스(폰트 CDN 등) 로드 — `stage0`의 Google Fonts 실증
- ❌ 진도/완료 상태 자체 집계 (앱 진도와 이중 장부)

### 3-6. 신규 콘텐츠 생성 규칙 〔A ✅ 확정 — 구조 게이트 후보〕

1. 모든 mc → `choiceExplanations`를 `choices`와 **동수로 완비** (확정 #1)
2. 모든 개념 블록 → `prerequisites` 챕터 **1개+ 명시 인용** (확정 #4). **최선두 챕터(앵커 A4)는 예외**
3. recall 소재 → **mc 변환 + 본문 인출 카드(채점 X) 병존** (확정 #5)
4. 모든 섹션 → `miniQuiz` ≥ 1. 빈 `quiz`는 **레거시 잔존 한정**
5. **예시는 개념 블록 내부 결합** (§1-4 P3 역설 방지)
6. **문항 소재 = 기존 콜아웃**(시험포인트/결정표/N문형) 직접 승격

### 3-7. Next.js 주의 2가지 — 권고안과 근거

| 주의 | 선택지 | **권고** | 근거 |
|---|---|---|---|
| ① **메타 export 명명**: `meta` vs `chapterMeta` | 기술 충돌은 **없다** — `metadata` 예약은 `app/` 라우트 파일 한정이고 `/content`는 라우트 밖(CURRICULUM §3 주의①이 이미 판단) | **`chapterMeta`** | 남는 비용은 전부 인간·도구 측이다. `meta`는 grep 시 HTML `<meta>`·주석 노이즈가 많은 반면 `chapterMeta`는 **리포 전체에서 유일한 시그니처** → 구조 게이트 G1을 `grep -L "export const chapterMeta"` 한 줄로 기계화 가능. 타이핑 7자 대비 이득이 큼 |
| ② **`"use client"` 위치**: 각 챕터 모듈 상단 vs 로더 래퍼 한 곳 | (a) 각 모듈 상단(단일 파일) → **§3-1 RSC 제약으로 meta 서버 소비 불가 → 사실상 배제** / (b) 로더 래퍼 한 곳 → 표준화는 기계적이나 완전 정적 챕터까지 전부 하이드레이션, 본문을 서버에서 실수로 렌더하면 런타임 오류를 관습으로만 방어 / (c) **2파일 분리 + `body.jsx` 상단 선언** | **(c)** | 포기하는 것은 **챕터 본문의 하이드레이션 비용뿐**이고, 본문 대부분이 인출 인터랙션(탭 공개)을 가져 어차피 클라이언트가 필요하다. 클라이언트 컴포넌트도 빌드 시 HTML은 프리렌더된다. `stage0`류 **완전 정적 챕터의 서버 컴포넌트 승격**은 v1을 바꾸지 않는 후속 최적화("`use client` 없는 body도 허용" 한 줄 완화)로 가능 |

#### 결정 1. 표준 형식 **팔레트** 구성 ← **이 제안서의 핵심**

- **상태**: **미확정** (CURRICULUM §3 "확정된 표준 형식 팔레트: (미확정)")
- **§1이 준 결론**: **점수로는 못 정한다.** 전 형식 동급(86.5% vs 86.2%), 유일한 차이 클러스터는 N=2로 증거 부족.

| 선택지 | 트레이드오프 | |
|---|---|---|
| **(a) 팔레트를 "형식"이 아니라 "성분 요구"로 정의** — 형식 자유, 단 모든 챕터가 `설명+예시(개념 내부 결합)+퀴즈+해설` 4성분을 갖출 것 | 점수 증거와 정합(형식은 동급, 변별은 **성분 완결성**에서 발생). jsx 하이브리드의 "본문 자유" 정신 유지. 대신 "팔레트 1~3개"라는 기존 표현을 성분 규정으로 대체해야 함 | **← 권고** |
