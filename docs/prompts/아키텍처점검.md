# 세션 프롬프트 — 아키텍처 건강검진 + 현행 구조 문서화

> **사용법**: 리포 루트에서 새 세션을 열고 플랜 모드(Shift+Tab 두 번)로 아래 "본문"을 투입한다.
> **산출물**: 아키텍처 진단 리포트 1개(`docs/ARCHITECTURE_REVIEW.md`) — 건강 루브릭 점수 + 진단 다이어그램(mermaid) + (발견 시) 실행 가능한 결함 이슈. 현행 구조 설명 자체는 자매 안내서의 산출물 `docs/ARCHITECTURE.md`를 기준선으로 삼는다 — 이 프롬프트는 그 안내서를 현실과 대조·채점한다.
> **관계**: 이 프롬프트는 **진단**이다. 현행 구조를 쉽게 설명하는 **안내서**는 자매 `docs/prompts/아키텍처안내.md`(산출물 `docs/ARCHITECTURE.md`)가 담당하며 그 파일의 정본 소유자다. 진단은 `docs/ARCHITECTURE.md`를 **소유하지 않는다** — 덮어쓰지 말고 기준선으로 읽고, 진단 결과는 `docs/ARCHITECTURE_REVIEW.md`에 쌓는다.
> **지위**: 재사용 후보. 한 번 돌려 유용하면 `.claude/skills/architecture-review/`로 승격한다 —
> 그때 §0 정독 목록·§4 산출물 골격은 그대로 두고, 이 프롬프트가 코드에서 재확인을 강제하는 구조(아래 "작업 원칙")를 유지하면 낡지 않는다.

## 본문 (아래부터 복사)

너는 이 세션에서 **아키텍처 진단 담당**이다. 이 프로젝트(`aws-reps`)는 Next.js 정적 사이트로 만드는 AWS DVA-C02 학습 앱이다. 네 임무는 두 가지다:

1. **주 임무** — 현재 코드베이스의 아키텍처를 **있는 그대로(as-built)** 정확히 문서화하고, 그 과정에서 구조적 건강 상태(기술부채·일관성 붕괴·경계 침범·리스크)를 진단한다.
2. **부차 임무** — 다가올 에픽(인프라·유저 기능·AI 채점)과 MVP(Phase1~4) 릴리즈 관점에서 현 구조의 준비도를 평가한다.

### 작업 원칙 (먼저 읽어라)
- **읽기 전용 진단이 먼저다.** 문서 산출물을 쓰기 전까지 앱·콘텐츠 코드를 수정하지 마라.
- **이 프롬프트의 요약을 믿지 말고 코드에서 직접 확인하라.** 프롬프트는 낡을 수 있다 — 경로·규약 버전·파일 수·데이터 모델은 실제 파일이 정본이다. 아래에 이름이 나오는 파일이 옮겨졌거나 사라졌으면 그 사실 자체를 발견으로 기록하라.
- 판단은 **근거 `파일:라인`**과 함께. 인상 비평 금지.

### 0. 기준 정독
- `CLAUDE.md` — 브랜치·과제·프로세스 규칙 (착지·이슈 규칙 포함)
- `content/schema.ts` — **규약 v3, 챕터 모듈 계약의 단일 진실.** 주석이 설계 근거·결정·위반 시 증상까지 담고 있다. 여기가 "무엇이 계약인가"의 정본.
- `docs/ARCHITECTURE.md` — 자매 안내서(`아키텍처안내.md`)의 산출물. 있으면 **as-built 기준선**으로 읽고 현실과 대조·채점한다. 없으면 코드에서 직접 as-built를 세워 진단만 남기거나 안내서 세션을 먼저 돌린다.
- `docs/APP_ARCHITECTURE_DRAFT.md` — **설계 *제안* 초안(구현물 아님).** 현행과 대조하는 기준으로만 쓴다. draft가 상정한 구조가 실제로 어떻게 구현/변형/폐기됐는지가 진단의 핵심 재료다.
- `docs/CURRICULUM.md`, `docs/VERIFIED_FACTS.md` — 있으면 훑기(콘텐츠 정책 맥락).

### 1. 지도 만들기 — 현행 구조 스캔 (읽기 전용)
아래를 **코드에서 직접** 확인해 각 축의 as-built 사실을 수집하라. (파일 이름은 출발점일 뿐 — 실제 트리를 봐라.)

- **스택·빌드·배포**: `package.json` 스크립트 체인(predev·prebuild·validate), `next.config.ts`의 `output: "export"`가 뜻하는 것(서버 런타임 없는 순수 SSG), `tsconfig.json`, `.github/workflows/`, Vercel(develop→프리뷰 / main→프로덕션).
- **라우팅·렌더링**: `app/` 트리. `generateStaticParams`/`dynamicParams=false`가 만드는 SSG 경계, 서버 컴포넌트 vs `"use client"` shim 목록, `loadBody()` 동적 import의 챕터별 청크 분리.
- **축1 — 콘텐츠 파이프라인**: `content/`의 2계층을 구분하라. ① 레거시 날것 원본(`content/*.jsx`, `/_source` 검수 대상, 앱이 import 금지·문자열+Babel) ② 구조화 챕터(`content/chapters/{id}/`, 규약 v3: meta·session·body·intro/outro·sections/NN.mdx·figs). 그리고 앱이 이걸 보는 경로: `content/registry.ts`(앱이 소비하는 유일 목록, **수동 등록**) → `lib/content.ts`(앱↔콘텐츠 **유일 통로**). 마이그레이션 현황을 수치로(구조화 N개 / 전체 원본 수)와 MDX 규정(remark/rehype 플러그인 금지 등)까지.
- **축2 — 상태·진도**: `lib/progress.ts`. localStorage 키·데이터 모델·hydration 처리(SSG는 빈 진도로 렌더 후 useEffect 충전), 로그인 없음. 진도 외 상태(퀴즈 시도 기록·오답노트)가 실제로 존재하는지 유무를 확인.
- **축3 — 빌드·툴링·하네스**: `scripts/`(`validate-content.mts`=tsc가 못 잡는 값 수준 계약 검사·prebuild 연결, `gen-source-routes.mjs`, `import-drills.mts`, `git_guard.py`=PreToolUse 훅). 검증 게이트가 규약의 **어떤 계약을 실제로 강제**하는지 규칙 단위로.

### 2. 건강검진 — 축별 진단 (주 목적)
각 축에서 아래를 판정하고, 발견마다 **심각도(높음/중간/낮음)·근거 `파일:라인`·영향 범위**를 붙여라.

- **일관성 (규약 vs 코드)**: `schema.ts`(규약 v3)가 선언한 계약과 실제 코드/데이터가 어긋나는 지점.
- **draft ↔ as-built 괴리**: `APP_ARCHITECTURE_DRAFT.md`가 상정한 구조(예: `lib/contract/` 어댑터 3파일, `dva.progress.v1`의 시도·정답 기록, `dva.review.v1` 오답노트, `app/review/` 화면)가 실제로 무엇으로 접혔거나 미구현인지. **각 괴리가 부채인지 합리적 단순화인지** 판정하라 — 이게 "현행 문서화"의 알맹이다.
- **경계 침범**: 선언된 경계가 지켜지는가 — "앱은 `content/`를 직접 import 하지 않는다", 본문 네거티브 규정(자체 내비·전역 스타일·window 접근·외부 리소스 금지), `registry.ts` 수동 등록의 확장성.
- **기술부채·중복·스케일 한계**: 죽은 코드, 평행 타입, 손으로 유지하는 목록이 챕터 4→28+로 갈 때의 한계.
- **static-export 천장**: 진도가 localStorage뿐이고 서버가 없다. 서버가 필요한 에픽(인증·DB·AI 채점)이 오면 `output: "export"`를 **어디서 어떻게 벗고 무엇이 깨지는가.** (이건 건강검진이자 §3 에픽 준비의 핵심 축.)
- **강건성**: 빈 `quiz`·`session` 없는 챕터·localStorage 파싱 실패 등 경계 조건 처리.

### 3. 부차 평가 — 에픽 준비도 + MVP
- **다가올 에픽**: 큐의 인프라·유저 기능·AI 채점 에픽이 현 구조 위에서 요구하는 변경의 크기. static→서버 전환 지점, 인증 도입 시 진도 모델 마이그레이션(로컬 → 계정 귀속), AI 채점이 요구하는 서버/데이터 계층.
- **MVP(Phase1~4)**: 릴리즈를 막는 **구조적** 결손이 있나. (콘텐츠 분량·품질은 범위 외 — 구조만 본다.)

### 4. 산출물 — 아키텍처 진단 리포트
`docs/ARCHITECTURE_REVIEW.md`를 **생성/갱신**한다(진단·건강검진 리포트). 현행 구조를 쉽게 설명하는 일은 자매 안내서 `docs/ARCHITECTURE.md`의 몫이니 여기서 재생성하지 말고, 그 안내서를 기준선으로 **대조·채점**하며 링크로 연결한다(`APP_ARCHITECTURE_DRAFT.md`는 제안 문서로 남긴다). `docs/ARCHITECTURE.md`가 아직 없으면 안내서 세션을 먼저 돌리거나, 이번엔 코드에서 직접 as-built를 세워 진단만 남긴다. 리포트는 다음을 담는다:

1. **한눈 요약** — 스택·배포·핵심 아키텍처 결정 3~5줄 + 루브릭 총점(§4-B).
2. **시각화 자료** — §4-A의 다이어그램들.
3. **축별 현행 구조** — 콘텐츠 파이프라인 / 상태·진도 / 빌드·툴링·하네스, as-built로.
4. **규약·경계** — 규약 v3 요지, 선언된 불변식과 그걸 지키는 게이트(validate-content·tsc·git_guard) 매핑.
5. **건강 진단** — 발견 목록(심각도·근거·영향). draft↔as-built 괴리 포함.
6. **루브릭 점수** — §4-B의 항목별 점수표.
7. **확장 지점** — static→서버 전환 경로, 에픽 준비도, MVP 구조 결손.

문서 톤은 이 리포 문서 스타일(간결·근거 명시·결정의 *이유*까지). 코드 참조는 `파일:라인`.

#### 4-A. 시각화 자료 (mermaid 코드블록 — `docs/`의 .md는 GitHub가 그대로 렌더한다. 앱 MDX 파이프라인과 무관하니 콘텐츠 코드펜스 규정에 얽매이지 않음)
아래를 각각 mermaid로 그린다. **실제 코드에서 확인한 것만 — 상상 금지**:
- **시스템 지도** (`flowchart`): 요청 → 라우트(`app/chapters/[id]/[sec]`) → `loadBody()` 동적 import → 콘텐츠 계약(schema/registry/lib) → 상태(localStorage)의 데이터 흐름. 서버 렌더 경계와 `"use client"` shim을 구분 표기.
- **콘텐츠 파이프라인** (`flowchart`): 레거시 날것 원본(`content/*.jsx`) → (수동 변환) → 구조화 챕터(`content/chapters/{id}/`) → `registry.ts` 수동 등록 → `lib/content.ts` → 앱 렌더. **마이그레이션된 것 / 남은 것**을 색·주석으로 구분.
- **빌드·검증 게이트** (`flowchart` 또는 `sequenceDiagram`): `predev`/`prebuild`/`validate-content`/`gen-source-routes`/`git_guard`가 각각 어느 시점에 무엇을 막는지.
- **static→서버 전환 (현행 vs 목표)**: 현재(순수 SSG·localStorage) 대 에픽 후(인증·DB·AI 채점 서버)를 나란히 — 무엇이 새로 필요하고 무엇이 바뀌나.
- (선택) **루브릭 점수 시각화**: mermaid엔 레이더가 없으니 표 + 텍스트 막대(█░)로 항목별 점수를 한눈에.

#### 4-B. 아키텍처 건강 루브릭 (재실행 시 점수 추세 비교용 — 항목·척도를 고정한다)
각 항목을 **1~5**로 채점하고 **1줄 근거 + 대표 `파일:라인`**을 반드시 붙인다. 점수는 근거에 매여 있어야 하며 인상 점수 금지.

척도: **1**=심각한 결손·릴리즈 차단 / **2**=동작하나 큰 부채 / **3**=동작·알려진 부채가 수용 가능 / **4**=견고·소소한 개선점 / **5**=모범.

| 항목 | 무엇을 보나 |
|---|---|
| 콘텐츠 파이프라인 | 2계층 분리, 마이그레이션 확장성(4→28+), MDX 규정 준수 |
| 상태·진도 | 모델 적합성, hydration 안전, 확장 여지(계정 귀속) |
| 빌드·툴링·하네스 | 검증 게이트 커버리지, CI, 재현성 |
| 규약·경계 일관성 | schema.ts 계약 준수, 선언된 경계 침범 없음, draft 괴리 관리 |
| 확장성·서버 준비도 | static→서버 전환 용이성, 에픽 수용력 |
| 강건성 | 빈 quiz·session 없는 챕터·파싱 실패 등 경계 조건 처리 |

총점 = 단순 평균(소수 1자리). 문서 상단(§4-1 한눈 요약)에 총점을 싣고, 표 아래에 **가장 낮은 2개 항목이 다음에 손볼 우선순위**임을 1~2줄로 명시한다. 같은 척도·같은 항목으로 다음 점검 때 재채점하면 점수 추세가 구조의 개선/퇴행을 드러낸다.

### 5. 이슈·착지
- 진단 중 **실제로 손봐야 할 결함**(오작동·구체적 부채)이 나오면 리포 규칙대로 GitHub 이슈로 등록하라(`/write-issue`). 단 문서를 채우려고 억지 이슈를 만들지 마라 — 문서가 주 산출물, 이슈는 실행 가능한 결함에 한정.
- 새 docs 파일도 리포 규칙상 하나의 작업 단위다. 완료 후 `/land`로 착지(기본 PR)한다.

### 금지
- 진단·문서화 완료 전 앱·콘텐츠 코드 수정 금지(문서 산출물 외).
- `content/` 수정 금지 — 문제가 보이면 고치지 말고 문서/이슈에 기록만.
- 이 프롬프트의 요약을 실제 코드보다 우선하지 마라.
