## 프롬프트 본문 (아래부터 복사)

너는 **문항 유형 체계 설계자**다. 이 프로젝트(DVA-C02 학습 웹앱)의 규약 v0는 문항을 4지선다(`choices[4]`) 하나로만 정의하는데, 실물 콘텐츠에는 그 외 유형이 존재한다는 것이 스트레스 테스트로 확인됐다. 네 임무는 **발견된 유형들을 학습 효과를 보존하면서 규약·앱·학습 루프에 통합하는 설계안**을 `docs/QUESTION_TYPES_DRAFT.md` 하나로 만드는 것이다. 섹션 완성 즉시 저장·커밋하라(몰아서 저장 금지).

### 0. 정독
- `docs/CONTRACT_PREWORK.md` §1 — 발견된 유형 목록과 사례 파일, 발견 #2(`options[].why`)
- `docs/CURRICULUM.md` §3 — 규약 v0의 Question 구조 원문
- `docs/RUBRIC.md` §8의 L1(인출 연습)·L2(해설 완전성) 앵커 — 유형 설계의 학습과학 판단 기준
- `docs/LEARNING_LOOP_DRAFT.md`가 존재하면 참조 — 숙달 판정·오답노트와의 인터페이스 (없으면 "문항 결과가 정답/오답 신호를 남긴다" 수준으로만 가정하고, 인터페이스 요구를 명시적으로 기록)

### 1. 유형 인벤토리 확정
CONTRACT_PREWORK §1의 유형 목록에서 출발해, `/content`에서 각 유형의 실물 예시를 1~2개씩 추가 확인하라(**읽기만** — 수정 금지). 목록에 없는 유형을 발견하면 추가하라. 각 유형마다 실물 인용(파일명 + 문항 요지)을 남겨라 — 이 문서의 설득력은 실물 근거에서 나온다.

### 2. 유형별 분석표
각 유형에 대해 4열로 분석하라:
1. **인출 강도** (L1 관점): 이 유형이 재인(recognition)인가 인출(recall)인가, 4지선다로 변환하면 무엇을 잃는가
2. **채점 가능성**: 자동 채점 가능 / 자기 채점 필요(자유 인출 카드처럼 사용자가 "맞았음/틀렸음"을 스스로 표기) / 채점 무의미(자기평가 체크리스트) — 자기 채점 유형은 정답 신호의 신뢰도 문제를 어떻게 다룰지 포함
3. **학습 루프 통합**: 오답노트 재출제·숙달 판정에 이 유형의 결과가 어떻게 들어가는가 (안 들어간다면 그것도 명시)
4. **렌더 요구**: 공용 컴포넌트로 수용 가능한가, 유형별 전용 컴포넌트가 필요한가

### 3. 스키마 설계안 (핵심)
다음 세 노선을 구체 코드 스케치와 함께 비교하라:
- **A. Discriminated union**: `type` 필드 + 유형별 전용 필드 (예: `type:"mcq"`는 `options[{text, why}]`, `type:"recall"`은 `prompt`/`modelAnswer`/`selfGrade:true`)
- **B. 4지선다 강제 통일**: 전 유형을 choices[4]로 변환 — 표준화 비용은 최소지만 L1 손실을 정량적으로 서술
- **C. 혼합**: v1은 2~3개 유형만 정식 채택, 나머지는 변환 또는 v2 연기
각 노선의 표준화 비용(CONTRACT_PREWORK의 파일당 견적 참조), 앱 복잡도(공용 Quiz 컴포넌트 분기 수), 학습 효과 보존을 비교하고 **권고안 하나**를 명시하라. 발견 #2의 `options[].why`(선택지별 해설)는 어느 노선이든 반영하라 — L2 앵커의 구조적 강제가 목적이다.

### 4. v1 채택 권고표
유형별로 `v1 정식 채택 / 4지선다 변환 / v2 연기` 중 하나를 권고하고 근거를 한 줄씩. **확정 어조 금지 — 전부 제안형이며, 최종 채택은 규약제안 세션(③)을 거쳐 인간이 ④에서 결정한다.** 표현 형식(레이아웃)의 우열 판정도 금지 — 그것은 축1 점수의 몫이다. 여기서 다루는 것은 "문항 유형을 규약이 표현할 수 있는가"라는 구조 문제뿐이다.

### 5. 완료 절차
QUESTION_TYPES_DRAFT.md 최종 커밋 → 종료 보고: 유형 수, 권고 노선, 인간이 골라야 할 결정 지점 목록. **BOARD.md는 수정하지 마라** — 병렬 세션 충돌 방지. 완료 보고만 하면 기록은 인간이 한다.
