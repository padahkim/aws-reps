## §1 스트레스 테스트 결과 — v0 × 실물 콘텐츠 3파일

표본 선정: 축2 리포트가 존재하는 7파일 중, 표현 형식이 가장 서로 다른 3개.
(형식 태그가 아직 리포트에 없어 육안 선별: 카드형 인출 세션 / 정적 HTML 문서 / 사이드바 강의 앱)

### 1-A. `dva-chapter-template.jsx` (1,005줄) — 카드형 인출연습 세션

**형식**: 모바일 폭 고정(460px) 단일 스크롤. 4종 학습 블록 — ①개념 인출 카드(Q→탭→A+why) ②인터랙티브 SVG 흐름도(역할→탭→서비스명) ③시나리오 퀴즈(자기설명 게이트: "오답 이유를 설명했어요" 버튼을 눌러야 해설 공개) ④혼합복습 카드(시나리오→서비스명 자유 인출). 상단에 4블록 진행률 레일. 데이터는 이미 파일 상단 `CHAPTER` 객체로 완전 분리되어 있음 — **7파일 중 v0 정신에 가장 가까운 실물**.

**meta에 담기지 않는 정보 (필드 부족)**:
- `line: "1"`, `eyebrow`, `subtitle` — v0 meta에 subtitle 없음 (title 하나로 합치면 손실은 경미)
- **복수 챕터 매핑**: 축2 리포트 기준 매핑이 "1-2·1-3·1-4 종합" — v0의 `id` 단수 체계로 표현 불가. 레거시 파일 상당수가 챕터 경계와 1:1이 아닐 것으로 예상 → meta에 `chapters[]`(복수) 또는 `coverage[]` 같은 매핑 필드가 필요하다는 첫 실증
- 교육 원리 태그(RETRIEVAL/DUAL-CODING/SELF-EXPLAIN/INTERLEAVING) — 블록별 주석 성격. meta 필드로 승격할 근거는 아직 없음(제안 안 함), 다만 표준화 시 버릴 정보인지 v1에서 판단 필요

**quiz 구조(scenario/choices[4]/answer/explanation)에 안 맞는 문항 유형**:
| 파일 내 유형 | v0 적합성 | 문제점 |
|---|---|---|
| `quizzes[]` (4지선다) | **거의 적합** | ① 해설이 `options[].why`(선택지별 4개)로 존재 — v0의 단일 `explanation`에 넣으면 오답별 조건화(축1 L2의 2점 앵커)가 문자열 안에 뭉개짐. SCHEMA_FEEDBACK_AXIS2 1행과 동일 발견 ② `answer`가 단수 인덱스 — v0는 `answer[]` 배열. 변환은 기계적(`[1]`로 감싸기) |
| `concepts[]` (Q/A/why 인출 카드) | **부적합** | 선택지가 없는 자유 인출 문항. choices[4]에 우겨넣으면 인출연습이 재인(recognition)으로 격하 — 콘텐츠 가치 훼손. quiz가 아닌 별도 유형 또는 본문 잔류 |
| `mixed[]` (시나리오→서비스명 + 대비 해설) | **부적합** | 동일하게 선택지 없음. `contrast`(인접 서비스와의 구분점) 필드도 갈 곳 없음 |
| `diagram` (역할→서비스명 인출 SVG) | **부적합** | 문항이자 도식인 중간물. 구조화 시도 자체가 과잉일 수 있음 — 본문 잔류가 자연스러움 |

**본문에서 분리하기 곤란한 인터랙션·상태**:
- 자기설명 게이트: "선택→오답 이유 설명 선언→해설 공개"는 **문항 데이터가 아니라 풀이 UX 정책**. 공용 `<Quiz>`로 문항을 옮기면 이 정책은 앱 셸의 동작이 되어야 함 — 규약이 "문항 데이터"와 "풀이 정책"을 분리해 주지 않으면 표준화 세션마다 임의 판단하게 됨
- 진행률 레일이 4블록 완료 상태를 집계 — 진도 저장(앱 요구사항)과 겹침. 본문 내 로컬 상태로 남기면 앱 진도와 이중 장부

**표준화 실작업량 추정**: **~40분, 판단 중심**. meta 생성 5분(기계적) + quizzes[]→v0 10분(기계적, 단 why 손실이 v1에서 해결 안 되면 손실 변환) + concepts/mixed/diagram 처분 판단 25분(v1이 유형을 정해주면 기계적으로 급감). **v1 설계가 이 파일의 작업량을 3배 좌우한다.**

### 1-B. `aws-dva-stage0.html` (531줄) — 정적 HTML 문서 (React 아님)

**형식**: 완결 HTML 문서. `<head>` 내 전역 CSS + Google Fonts 링크, 정적 SVG 도식 4개, 표, EXAM POINT 박스, 말미에 "이 문장이 술술 나오면 통과" 자기평가 체크리스트(문장+빈출도 ★). 인터랙션 전무.

**meta에 담기지 않는 정보**:
- 섹션별 빈출도(★★★/★★☆/★☆☆) 및 체크리스트 항목별 빈출도 — v0에 대응 없음 (SCHEMA_FEEDBACK 13행 `selfCheck[]{statement, freq}` 제안과 동일 발견). 이 파일에선 빈출도가 **섹션 헤더에도** 붙어 있어 문항 속성이 아니라 콘텐츠 구획 속성이기도 함
- 매핑: 축2 기준 0-1 (+0-2 일부 겹침) — 1-A와 같은 복수 매핑 문제

**quiz 부적합 유형**: 퀴즈 성분 자체가 X (축2 태그 일치). 체크리스트는 "문항"이 아니라 서술형 자기평가 — choices[4]로 변환 불가·무의미. v0로는 이 파일의 quiz export가 빈 배열이 되는데, **"quiz 없는 챕터 모듈"이 규약상 적법한지** v0가 말해주지 않음 (앱의 `<Quiz>`·진도·오답노트가 quiz 존재를 전제하면 런타임 경계 문제)

**분리 곤란한 인터랙션·상태**: 없음 — 역으로 이 파일은 **완전한 서버 컴포넌트가 될 수 있는 실증 표본**. "use client"를 로더에서 일괄 선언하면 이런 파일마저 CSR로 끌려간다 (§2-1의 실물 근거)

**변환 이슈 (jsx 문법 외)**: ① HTML→JSX 기계 변환(class→className, style 태그 처리) 표면적이 큼 ② **Google Fonts 외부 링크** — 콘텐츠 파일이 외부 리소스를 끌고 오는 것을 규약이 금지/허용할지 결정 필요 ③ 전역 CSS(body, table 등 요소 셀렉터)가 앱에 로드되면 다른 챕터·앱 셸까지 오염

**표준화 실작업량 추정**: **~35분, 대부분 기계적**. HTML→JSX 25분(기계적, 자동화 여지) + 스타일 스코핑 처리 10분. 판단 요소는 체크리스트의 처분(v1에 selfCheck 유형이 생기면 기계적)뿐.

### 1-C. `aws-dva-s3-guide.jsx` (802줄) — 사이드바 강의 앱

**형식**: 파일 자체가 **완결된 미니 앱** — 사이드바 목차(그룹 3개), 강의 번호(115~155), 섹션별 빈출도 배지(2~5), 이전/다음 페이저, 모바일 햄버거 메뉴, "여기까지가 퀴즈 N 범위" 배너(GROUP_QUIZ). 섹션 데이터는 `SECTIONS[]` 배열로 분리돼 있으나 **body가 JSX 노드**(md 아님), 로컬 프레젠테이션 컴포넌트(KP/Warn/Exam/Code/DBox/Arrow/Diagram) 사용.

**meta에 담기지 않는 정보**:
- 섹션별 `no`(원 강의 번호 — 레거시 출처 추적용), `freq`(빈출도 2~5), `group`(기초/고급/보안) — v0 Section에 대응 없음
- **`GROUP_QUIZ` — 그룹→외부 퀴즈 범위 매핑** ("여기까지가 퀴즈 8 범위"): 콘텐츠와 퀴즈가 분리 생성되는 구조에서 인출 시점을 지정하는 정보. SCHEMA_FEEDBACK 17행 `quizScopeRef` 제안과 동일 발견 — **§2-4의 quiz `scope` 어휘 설계의 직접 입력**
- 역방향 갭: v0 Section의 `objectives[]`·`examples(md)`는 이 파일에 대응물 없음(examples는 본문 내 산재). v0 필드 중 "쓰임이 확인 안 되는 필드" 후보

**quiz 부적합 유형**: 파일 내 문항 0개 — 퀴즈는 외부 존재를 참조만 함. 1-B와 같은 "quiz 없는 모듈" 문제 + 외부 퀴즈 범위 참조라는 새 요구.

**분리 곤란한 인터랙션·상태 — 3파일 중 최악**:
- **앱 셸 침범**: 사이드바 내비·페이저·모바일 메뉴·스크롤 제어(`useEffect`+`document.getElementById`)는 챕터 콘텐츠가 아니라 앱의 일 (PLAYBOOK "앱 = 규약 export만 소비하는 셸"과 정면 충돌). 표준화 시 이 껍데기를 **벗겨내고** SECTIONS body만 남겨야 함 — 기계 변환이 아니라 절제 수술
- **전역 `<style>` 태그**: 요소 셀렉터(table, th, td…) 포함 — 여러 챕터가 한 앱에 로드되면 상호 오염. 규약이 스타일 스코핑 방식을 정하지 않으면 파일마다 다른 해법이 나옴
- 디자인 토큰 `C`가 파일마다 다름(1-A는 다크, 1-C는 라이트) — 앱 통합 시 시각 일관성 문제. 규약 범위인지 앱 범위인지 결정 필요
- KP/Warn/Exam 등 로컬 컴포넌트 — SCHEMA_FEEDBACK 13행 `callouts` 제안과 연결. 공용 컴포넌트 라이브러리로 승격할지, 챕터 로컬 허용할지

**표준화 실작업량 추정**: **1.5~2시간, 판단 중심**. 셸 제거·본문 재구성 60분 + 스타일 스코핑 30분 + 공용 콜아웃 치환 여부 판단 20분. 이런 "미니 앱형" 파일이 대기 큐 20개 중 다수라면 표준화 단계 견적을 지배한다.

### 1-D. 종합 — v0가 놓치고 있는 것 (우선순위순)

1. **문항 유형이 4지선다 하나뿐** — 실물엔 최소 4유형 더 존재: 자유 인출 Q/A 카드, 시나리오→서비스명(+contrast), 서술형 자기평가(selfCheck+freq), 도식 인출. 전부 choices[4]로 욱여넣으면 인출→재인 격하로 콘텐츠 가치가 죽는다. **v1 결정 필요: quiz 배열에 `type` 판별 필드를 두는 다형 구조 vs 4지선다 외 유형은 본문 잔류**
2. **선택지별 해설 부재** — `options[].why`(1-A 실물) vs v0 단일 `explanation`. 축1 L2 앵커(오답의 조건화)가 스키마 수준에서 강제되려면 선택지별 해설 필드 필요 (SCHEMA_FEEDBACK 1행과 수렴)
3. **본문 금지 목록이 없음** — "본문은 jsx 자유 표현"만으로는 1-C 같은 앱 셸 침범(자체 내비·페이저·전역 스타일·document API)을 막지 못한다. **v1에 본문 네거티브 규정 필요**: 예) 자체 내비게이션 금지, 전역 셀렉터 스타일 금지, document/window 직접 접근 금지, 외부 리소스(폰트 CDN) 금지
4. **복수 챕터 매핑 불가** — 레거시 파일은 커리큘럼 챕터와 1:1이 아님(1-A: 3챕터, 1-B: 1.5챕터). meta에 단수 id만 있으면 표준화 때 강제 분할 또는 허위 매핑
5. **quiz 없는 모듈의 적법성 미정** — 7파일 중 5파일이 퀴즈 성분 X(축2 태그). v0가 quiz export를 필수로 하는지, 빈 배열 허용인지, 앱이 어떻게 강건해야 하는지 미정
6. **퀴즈 범위 참조 없음** — "여기까지가 퀴즈 N 범위"(1-C) 같은 인출 시점 설계 정보의 자리 없음 → §2-4
7. **빈출도(freq) 정보의 자리 없음** — 섹션 헤더(1-B·1-C)와 자기평가 문장(1-B) 양쪽에 실존. 버리기엔 학습 우선순위 정보로 가치 있음
8. **풀이 정책과 문항 데이터의 미분리** — 자기설명 게이트(1-A)는 UX 정책. 공용 `<Quiz>`의 동작 옵션으로 승격할지, 폐기할지 결정 필요
9. **스타일·컴포넌트 규약 부재** — 전역 스타일 스코핑 방식, 디자인 토큰 소유권(앱 vs 챕터), 공용 콜아웃(KP/Warn/Exam) 라이브러리 여부
10. (운영) **작업량 프로파일**: 카드형(1-A) 40분·정적 문서형(1-B) 35분·미니 앱형(1-C) 2시간 — 표준화 견적은 파일 수가 아니라 **형식 유형 분포**로 잡아야 함. 축2의 형식 태깅(PLAYBOOK §5 지시 2)이 이 견적의 입력이 된다

## §2 기술 결정 포인트 분석 (평가-독립 · Next.js App Router 관점)

> 전부 제안형. 표현 형식의 우열은 다루지 않는다. §2-0의 발견이 §2-1·§2-3의 선택지를 재편하므로 먼저 읽어야 한다.

### §2-0. 선행 발견 — 두 결정을 지배하는 RSC 제약 하나

**"use client"가 선언된 모듈의 비컴포넌트 export(meta 같은 순수 데이터)는 서버 컴포넌트에서 import해 사용할 수 없다** (클라이언트 경계를 넘는 모든 export가 클라이언트 참조로 바뀜). 그런데 meta는 서버 소비가 필수다 — `generateStaticParams`(SSG 경로 생성), 내비게이션 목록, `generateMetadata`(페이지 타이틀). 즉:

- 챕터 모듈 상단에 "use client"를 쓰면 → 같은 파일의 meta를 서버가 못 읽는다
- 반대로 meta를 읽으려고 단일 파일을 서버 그래프에 넣으면 → 내비가 전 챕터의 **본문 코드까지** 번들에 끌어들인다 (tree-shaking이 sideEffects 설정에 의존해 불안정)

**제안: 챕터 모듈을 데이터/본문 2파일로 분리**하면 이 제약이 소멸하고 §2-1·§2-3이 전부 단순해진다:

```
content/chapters/{id}/
  meta.ts    ← chapterMeta + quiz (순수 데이터, 서버 안전, "use client" 금지)
  body.jsx   ← "use client" + default export 본문 컴포넌트
```

비용: 파일 2개 관리(표준화 시 기계적 분할). 효익: 서버/클라 경계가 파일 경계와 일치 — 규약 위반을 grep으로 검사 가능(신규 모드 G1 게이트에 유리).

### §2-1. "use client" 선언 위치

| 선택지 | 트레이드오프 |
|---|---|
| (a) 각 챕터 모듈 상단 (단일 파일) | §2-0 제약으로 meta 서버 소비 불가 → 레지스트리에 meta 중복 기재 강요. **사실상 배제** |
| (b) 로더 래퍼 한 곳 (클라이언트 래퍼가 dynamic import) | 표준화가 기계적(파일별 판단 없음). 대신 1-B 같은 완전 정적 챕터도 전부 하이드레이션 대상. meta는 무지시자 모듈이라 서버가 읽을 수 있으나, 본문 컴포넌트를 서버 그래프에서 실수로 렌더하면 런타임 오류 — 관습으로만 방어 |
| (c) **2파일 분리 + body.jsx 상단 선언 (제안)** | "use client"가 본문 파일에만, 파일 단위로 존재. 로더·레이아웃·내비는 서버 컴포넌트 유지. 정적 챕터도 SSG 프리렌더 HTML은 유지되고(클라이언트 컴포넌트도 빌드 시 HTML 프리렌더됨) 지불하는 건 하이드레이션 JS뿐 |

**권고: (c).** 포기하는 서버 컴포넌트 이점의 범위 = 챕터 본문의 하이드레이션 비용뿐이며, 본문 대부분이 인출 인터랙션(탭 공개)을 갖는 이 프로젝트 특성상 어차피 클라이언트가 필요하다. 1-B류 완전 정적 챕터의 서버 컴포넌트 승격은 v1 규약을 바꾸지 않는 후속 최적화로 가능("use client" 없는 body도 허용하는 완화 한 줄).

### §2-2. 메타 export 명명 — `meta` vs `chapterMeta`

- Next 예약어 `metadata`는 **app/ 라우트 파일에만** 적용되므로 /content 모듈의 `meta`가 기술적으로 충돌하지는 않는다. 비용은 전부 인간·도구 측: `metadata`와의 시각적 혼동, 에디터 자동완성 오도, 코드 리뷰 시 혼선
- `meta`는 짧지만 grep 시 HTML `<meta>`·주석 등 노이즈가 많다. `chapterMeta`는 리포 전체에서 유일한 시그니처 — 신규 모드 구조 게이트(G1)를 `grep -L "export const chapterMeta"` 수준으로 기계화 가능

**권고: `chapterMeta`.** 타이핑 비용 7자 대비 혼동 제거·게이트 기계화 이득이 크다. (대안으로 `export const chapter = { meta, quiz }` 단일 루트도 검토했으나, quiz만 소비하는 오답노트·채점 코드가 매번 한 겹 벗겨야 하고 부분 import가 안 돼 이득이 없다 — 비채택 제안으로만 기록)

### §2-3. 챕터 동적 로딩 전략

/content가 app/ 라우트 밖에 있으므로 빌드 포함은 **정적으로 분석 가능한 import 문**으로만 보장된다. 선택지:

| 선택지 | 평가 |
|---|---|
| (a) **명시적 레지스트리 + next/dynamic (제안)** | `content/registry.ts`가 meta.ts 전부를 정적 import(순수 데이터라 저비용) + body는 `next/dynamic(() => import("./chapters/s3/body"))` 맵. 챕터별 별도 청크로 코드 스플리팅 자동. 챕터 추가 = 레지스트리 1행 — 27개→100개 규모에서도 선형 |
| (b) 템플릿 문자열 동적 import (`import(\`@/content/${id}\`)`) | 번들러가 디렉터리 전체를 컨텍스트로 포함 — legacy 쓰레기까지 빌드에 들어가고 타입 안전성 없음. 배제 |
| (c) fs 읽기 + 빌드타임 컴파일(MDX류) | "콘텐츠=코드 모듈" 결정과 충돌하는 별도 아키텍처. 배제 |
| (a′) 레지스트리 자동 생성(codegen) | (a)의 자동화. 챕터 30개 이상부터 검토할 후속 개선 — v1 규약 변경 없이 도입 가능 |

**권고: (a).** `generateStaticParams`는 레지스트리 키에서 파생 → `app/chapters/[id]`가 전 챕터를 SSG. 내비·진도 화면은 meta.ts만 소비하므로 본문 청크를 로드하지 않는다(§2-0 분리의 직접 효익).

### §2-4. `quiz` 필드 설계

스트레스 테스트 입력: 선택지별 해설(1-A), 외부 퀴즈 범위 배너(1-C), 비정형 문항 4유형(§1-D-1), 퀴즈 없는 모듈(1-B·1-C).

```ts
// v1 초안 제안 (전부 제안형)
type Question = {
  id: string;          // 규칙: "{챕터id}-q{2자리}" 예: "s3-q01" — 전역 유일.
                       // 오답노트·진도 localStorage 키가 챕터 밖에서 문항을 지시해야 하므로 챕터 접두 의무화 제안
  type: "mc";          // v1은 "mc"(4지선다)만 정식. flashcard·selfcheck 등은
                       // 후보 어휘로 예약만 하고 본문 잔류 (§1-D-1의 인출→재인 격하 방지)
  scope: string;       // 어휘 제안: "section:{섹션슬러그}" | "chapter" (종합)
                       // — 1-C의 "여기까지가 퀴즈 N 범위"를 section 나열로 흡수. 자유 문자열 금지
  concept: string[];   // 최소 1개 의무 제안 — 혼합복습(축1 L8)·오답노트 분류가 이것 없이는 불가능.
                       // 어휘 통제는 v1에선 미도입(챕터 내 자유), 교차 챕터 어휘 사전은 v2 과제
  scenario: string;
  choices: [string, string, string, string];  // 4개 고정 제안 — 레거시 3지선다는 오답 1개 보충 생성
  answer: number[];    // 복수 정답 대응 (v0 유지)
  explanation: string;               // 정답의 근거
  choiceExplanations?: [string, string, string, string];  // 선택지별 why — 1-A 실물·SCHEMA_FEEDBACK 1행.
                       // v1에서 optional로 시작, 신규 모드 게이트에서 의무화 여부는 인간 결정 포인트
};
export const quiz: Question[];  // 빈 배열 적법 (퀴즈 성분 X 파일 다수 — 1-B·1-C). 앱은 빈 quiz에 강건해야 함
```

미해결 결정 포인트(인간 몫): ① `choiceExplanations` 의무화 시점 ② 비정형 유형(flashcard/selfcheck)을 v1.1에서 정식 type으로 승격할지 ③ freq(빈출도)를 Question이 아닌 섹션/챕터 meta 어디에 둘지.

### §2-5. 본문 내 문항 배치 API — `<Quiz />` 인터페이스 초안

본문(body.jsx)이 문항 데이터를 중복 소유하지 않고 위치만 지정하는 인터페이스:

```tsx
// 로더(서버) → ChapterProvider(클라)가 해당 챕터의 quiz 배열을 컨텍스트로 주입
<Quiz ids={["s3-q01", "s3-q02"]} />        // 명시 나열 — 기본형. grep 가능, 리팩터에 강함
<Quiz scope="section:versioning" />        // 편의형 — quiz[].scope로 필터. ids와 상호배타
<Quiz scope="chapter" />                   // 챕터 종합(finalQuiz 상당)
```

- 데이터 흐름: `<Quiz>`는 props로 문항을 받지 않는다 — ChapterProvider 컨텍스트에서 ids/scope로 조회. 본문과 문항 데이터의 결합이 **문자열 id 참조**로만 존재 → 규약 v1이 바뀌어도 본문 수정 불요
- 채점·진도·오답노트 기록은 전부 `<Quiz>` 내부(앱 셸 책임). 자기설명 게이트(1-A) 같은 풀이 정책은 `<Quiz mode="self-explain">` 식 옵션으로 승격 가능하나 v1 기본은 미포함 — 인간 결정 포인트
- 존재하지 않는 id 참조는 빌드/테스트 타임 검증 대상 (레지스트리 기반 정적 검사 스크립트 1개로 가능)
