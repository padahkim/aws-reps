> **지위**: 이 문서는 평가 워크스트림의 단일 진실 공급원(single source of truth)이다. 축1/축2 세션 프롬프트와 한 세트로 동작한다. **AI는 이 문서를 수정할 수 없다 — 수정 권한은 인간에게만 있다.** 이 문서와 다른 기준을 쓰고 싶다면 제안만 하고 승인을 기다려라.

## 1. 프로젝트 컨텍스트

**무엇을 만드는가**: AWS Certified Developer – Associate(DVA-C02) 시험 대비 학습 웹앱. 핵심 설계 원칙은 **앱 코드와 학습 콘텐츠의 완전 분리** — 콘텐츠는 `/content`의 데이터 파일로만 존재하고 앱은 렌더링만 한다. 앱은 콘텐츠가 비어 있어도 동작해야 한다.

**시험 정보 (평가의 최종 기준점)**:
- DVA-C02. 도메인 비중: 개발 32% / 보안 26% / 배포 24% / 트러블슈팅·최적화 18%. 65문항 130분, 720/1000 합격
- 시험의 성격: 정의 암기가 아니라 **구현 판단** — 시나리오 속에서 서비스·옵션·원인을 고르게 한다. 문제에 "가장 비용 효율적인", "운영 오버헤드가 가장 적은", "코드 수정 없이" 같은 키워드가 숨어 정답을 좁힌다. 매력적 오답(다른 상황에선 정답인 선택지)이 특징
- 2024년 12월 업데이트로 EventBridge·이벤트 기반 아키텍처·복원력 패턴의 비중이 상승

**평가의 유일한 기준**: "이 콘텐츠로 공부한 사람이 실제 시험 문제를 맞힐 수 있는가." 문장이 유려한지, 분량이 많은지는 기준이 아니다.

**워크스트림 지도** (이 문서는 ③ 담당):
① 앱 개발 — 별도 핸드오프 프롬프트로 진행 (진단 → 리팩터링/재작성 결정 → 마일스톤 구현)
② 콘텐츠 생성 — 챕터별 생성 프롬프트로 별도 세션에서 진행, `/content`에 파일로 주입
③ **콘텐츠 평가 — 이 문서.** 기존(레거시) 콘텐츠의 구조조정과 신규 콘텐츠의 품질 게이트

## 3. 콘텐츠 스키마 v0 — 가설 지위

```
Chapter { id, phase(0~5), title, domain, examWeight, prerequisites[], sections[], finalQuiz[] }
Section { id, title, objectives[], body(md), examples(md), examPoints[], miniQuiz[] }
Question { id, scenario, choices[4], answer[](복수 가능), explanation }
```

**지위**: 레거시 모드에서 이 스키마는 **검증 대상 가설**이지 판정 기준이 아니다. 평가를 통해 수집된 피드백(§7·§8의 SCHEMA_FEEDBACK)을 인간이 검토해 v1로 확정한 후에만 신규 모드의 게이트 기준이 된다. 이렇게 시점을 분리해 "스키마가 기준이면서 산출물"인 순환참조를 끊는다.

## 4. 평가 철학과 역할 분담

- **인간의 역할**: 이 문서(기준)의 소유·수정, 캘리브레이션(초기 2~3건 판정 동의 확인), 「재작성」 판정 표본 확인, 경계 사례 최종 결정, 스키마 v1 확정
- **AI의 역할**: 기준의 일관된 적용, 전수 평가, 실행 가능한 수정 지시 생성. 기준 없는 AI 평가는 세션마다 흔들리고 길고 그럴듯한 글에 후해지므로, 이 문서의 체크 항목·앵커로만 판단하라. 취향 기준(문체·어조 선호) 반입 금지
- **캘리브레이션 규칙**: 어느 축이든 처음 사용하는 세션은 2~3개 파일만 평가하고 멈춰 판정 근거를 보고한다. 인간 동의 후 전수 진행. 판정이 인간 감각과 어긋나면 인간이 앵커를 수정한다 — AI가 앵커를 재해석하지 않는다

## 5. 파이프라인과 모드

### 현재 모드: **레거시**  ← 스키마 v1 확정 시 인간이 「신규」로 갱신

### 실행 순서와 그 이유
**0차 검사 → 축2(사실·시험 정합성) → 축1(학습 설계)** 순서는 고정이다.
- 축2가 먼저인 이유: 축1의 평가 대상(해설·예시·시험 포인트)은 사실 위에 선 구조물이라, 사실이 수정되면 학습 설계 평가도 무효가 된다. 정확성 게이트 → 전달력 평가 순서
- 0차가 먼저인 이유: 축2는 MCP 호출이 드는 비싼 패스다. 내용이 없는 파일에 토큰을 쓰지 않는다
- **두 축은 같은 세션에서 연달아 돌리지 않는다**: 축2가 끌어온 문서 덤프가 컨텍스트에 남은 채 축1을 판단하면 정확도가 떨어진다. 축2는 리포트 파일만 남기고, 축1은 원본 + 그 리포트만 읽는다

### 레거시 파이프라인 (전체 로드맵)
1. 0차 성분 검사 → 컬/성분 태깅 (§7)
2. 축2 평가 → `reports/axis2/` (§7)
3. 축1 평가 → `reports/axis1/` (§8)
4. [전 파일 완료 후 · 인간] SCHEMA_FEEDBACK 2종 검토 → **스키마 v1 확정**
5. 변환: 생존 콘텐츠를 v1로 기계 변환(내용 수정 금지), 결손 성분은 보충 생성 목록대로 별도 생성
6. 이 문서의 모드를 「신규」로 갱신 → 이후 신규 파이프라인: 0차 구조 게이트(스키마 포함) → 축2 → 축1

### 산출물 경로 지도
| 파일 | 작성자 | 용도 |
|---|---|---|
| `reports/axis2/{id}.md` | 축2 | 축1의 입력, 최종 판정의 절반 |
| `reports/axis1/{id}.md` | 축1 | 최종 판정의 절반 |
| `docs/EXAM_TASK_MAP.md` | 축2(부트스트랩) | 시험 가이드 Task ↔ 챕터 매핑 |
| `docs/VERIFIED_FACTS.md` | 축2 | 검증 사실 캐시 (재검색 방지 = 토큰 절약) |
| `docs/SCHEMA_FEEDBACK_AXIS2.md` | 축2 | 스키마 v1 확정용 제안 (사실·범위 관점) |
| `docs/SCHEMA_FEEDBACK_AXIS1.md` | 축1 | 스키마 v1 확정용 제안 (학습 설계 관점) |

최종 판정 = 두 리포트의 종합. 어느 한쪽이 「재작성/재구성」이면 전체 재작성.

## 6. 워크트리 병렬 운영 규칙

두 축은 별도 git 워크트리·별도 세션에서 병렬 운영할 수 있다. 단 **완전 동시가 아니라 파이프라인 병렬**이다 — 축1은 축2 리포트가 존재하는 파일만 처리할 수 있다.

- **브랜치**: 축2는 `eval/axis2` 워크트리, 축1은 `eval/axis1` 워크트리에서 작업한다
- **쓰기 경계 (충돌 방지 — 엄수)**:
  - 축2 쓰기 허용: `reports/axis2/**`, `docs/EXAM_TASK_MAP.md`, `docs/VERIFIED_FACTS.md`, `docs/SCHEMA_FEEDBACK_AXIS2.md`
  - 축1 쓰기 허용: `reports/axis1/**`, `docs/SCHEMA_FEEDBACK_AXIS1.md`
  - **둘 다 금지**: 콘텐츠 원본 수정(평가만 한다 — 수정은 별도 작업), RUBRIC.md·CURRICULUM.md 수정, 상대 축의 산출물 수정
- **동기화 (워크트리 간 파일은 커밋으로만 넘어간다)**: 축2는 파일 3~5개 평가마다 커밋한다. 축1은 세션 시작 시와 배치 사이마다 `git merge eval/axis2` (또는 `git checkout eval/axis2 -- reports/axis2 docs/VERIFIED_FACTS.md`)로 최신 리포트를 가져온다. 축2 리포트가 아직 없는 파일은 건너뛰고 대기 큐로 보고한다
- **완료 시**: 인간이 두 브랜치를 main에 머지한다 (쓰기 경계를 지켰다면 충돌 없음)
- **MCP 전제**: AWS MCP는 반드시 `--scope project`로 등록해 `.mcp.json`이 리포에 커밋되어 있어야 한다. local 스코프는 경로 기준이라 워크트리(다른 디렉터리)에서 보이지 않는다. 축1은 MCP 불필요

## 7. 축2 프로토콜 — 사실·시험 정합성 (1차 패스)

**역할**: AWS 공식 문서와 DVA-C02 시험 가이드를 근거로 **사실 정확성과 시험 정합성**을 검증하는 검수자. 문장력·학습 설계는 보지 않는다(축1의 일).

**철칙 — 근거 URL 없는 검증은 무효**: "검증됨" 판정에는 MCP 도구가 반환한 문서 URL을 반드시 첨부한다. 학습 지식만으로 검증 완료 표시 금지. 학습 지식과 문서가 충돌하면 문서가 이긴다. URL 미확보 항목은 `미검증`으로 남기고, 핵심 개념에 걸려 있으면 판정 보류.

### 7-1. 0차 검사 (MCP 사용 전, 파일당 30초)

**레거시 모드 → 성분 검사** (이 검사에서 "스키마"라는 단어를 쓰지 마라. 형식·구조는 보지 않는다):
- 컬 조건(즉시 제외, MCP 지출 금지): C1 빈 파일·생성 끊김·목차만 있는 껍데기 / C2 실질 중복(완전한 쪽만 유지) / C3 커리큘럼 어느 챕터에도 매핑 불가한 주제
- 컬이 아닌 파일에 **성분 태그**: `설명(O/X) · 예시(O/X) · 퀴즈(O/X) · 해설(O/X)` + 매핑 챕터 id
- **성분 결손은 컬 사유가 아니다.** 좋은 설명만 있는 파일도 온전한 평가 대상. 결손은 변환 단계의 보충 생성 목록 입력일 뿐

**신규 모드 → 구조 게이트** (스키마 v1 확정 이후이므로 정당): G1 스키마 위반 렌더링 불가 / G2 퀴즈 있는 섹션 절반 미만 or finalQuiz 부재 / G3 담당 범위 밖 주제 / G4 해설 없는 퀴즈 30%↑ → 하나라도 해당 시 즉시 「재작성」, MCP 중단

### 7-2. 부트스트랩 (최초 1회, 산출물 이미 있으면 생략)
1. 시험 가이드 확보: `aws___search_documentation`("DVA-C02 exam guide") → 실패 시 WebFetch `https://docs.aws.amazon.com/aws-certification/latest/examguides/developer-associate-02.html`
2. `docs/EXAM_TASK_MAP.md` 생성: 도메인 1~4 Task statement의 동사(구현/보호/배포/트러블슈팅)와 기술 키워드 추출 → 챕터 매핑 `| Task | 동사 | 기술 키워드 | 담당 챕터 |`. 무매핑 Task는 커리큘럼 갭으로 보고
3. `docs/VERIFIED_FACTS.md` 초기화: `| 서비스 | 주장 | 확인된 값 | 근거 URL | 확인일 |`

### 7-3. 본 검증 — 형식 무관 원칙
자유 마크다운이든 JSON이든 "이 텍스트가 주장하는 사실"과 "다루는 범위"를 평가한다. 레거시 모드에서 형식을 이유로 감점 금지.

- **F1 Task 커버리지**: EXAM_TASK_MAP에서 담당 Task·키워드 로드 → 누락 키워드 목록화, 이름만 스치면(정의 1줄, 예시·연습 없음) "표면 커버" 표기, 담당 밖 주제가 분량 차지하면 "범위 이탈"(축1 L5가 참조)
- **F2 사실 정확성 — 주장 유형별 강도**: ①수치(한도/기본값/기간/크기): 전수 검증 필수(AI 오류 최다 지점) ②동작 서술: 퀴즈 정답·시험 포인트에 걸린 것 필수, 부차는 의심스러운 것만 ③권장사항: 근거 찾으면 URL, 아니면 "일반 통념" 표기(오류 판정 금지)
  절차: a.서비스 단위 배치 → b.VERIFIED_FACTS 캐시 우선(적중 시 재검색 금지) → c.스니펫 우선, 불가할 때만 `read_documentation`, 같은 문서 세션 내 재조회 금지 → d.판정 `확인됨(값+URL)`/`수정 필요(현재→올바른 값+URL)`/`확인 불가` → e.신규 사실 캐시 추가
- **F3 출제 각도 정합**: 담당 Task 동사와 콘텐츠 관점 대조. "구현하라"인데 정의 나열이면 부정합, "트러블슈팅하라"인데 오류 시나리오 없으면 부정합. 개념 블록 단위로 지적
- **F4 퀴즈 정답 검증** (퀴즈 성분 있는 파일만): 모든 정답·해설 속 사실을 F2 절차로 검증. 정답 오류 시 — 레거시: **해당 문항만 폐기 목록**, 평가 계속 / 신규: 챕터 전체 「재작성」

### 7-4. 스키마 피드백 수집 (레거시 전용, 판정과 분리)
스키마 v0가 표현 못 하는 가치 있는 구조(비교표, 치트시트, 결정 트리, 실습 절차) 또는 쓰임이 확인 안 되는 필드를 발견하면 `docs/SCHEMA_FEEDBACK_AXIS2.md`에 `| 발견 파일 | 구조 | 제안 | 근거 |`로 기록. **스키마 직접 수정 금지 — 제안만.**

## 8. 축1 프로토콜 — 학습 설계 (2차 패스)

**역할**: 인지과학 기반 학습 설계(인출 연습·간격 반복·인지부하) 리뷰어. 사실 재검증 금지(축2 완료). "**이 구성이 기억에 남고 실전 풀이 능력으로 전이되는가**"만 본다. MCP 불필요.
**실행 조건**: `reports/axis2/{id}.md`를 먼저 읽고 모드·성분 태그 확인. 리포트 없으면 그 파일은 건너뛰고 대기 큐로 보고.

**채점 단위**: **개념 블록**(하나의 주제를 다루는 설명 덩어리). 스키마 Section이든 자유 마크다운 헤딩이든 개념 블록을 식별해 평가. 레거시 모드에서 형식·구조 감점 금지. 각 항목 0/1/2점, 흔들리면 앵커와 대조. 앵커 밖 취향 기준 금지.

**N/A 규칙 (레거시)**: 퀴즈 성분 X → L1·L2·L7·L8 N/A, 총점 모수 제외(L3~L6 만점 8점 기준). finalQuiz만 없으면 L8만 N/A. N/A 판정에는 「부분 평가」 명기 + 결손 성분을 보충 생성 목록으로 기록. (퀴즈 없다는 이유로 훌륭한 설명을 0점 폭탄으로 죽이지 않기 위함)

### 항목과 앵커
- **L1 인출 연습 밀도**: 0=블록에 문항 없음·챕터 끝에만 몰림 / 1=블록마다 있으나 방금 읽은 문장 되묻기("Lambda 최대 타임아웃은?") / 2=적용해야 풀림("실행이 900초에 중단됐다. 원인은?")
- **L2 해설 완전성**: 0="정답: C" / 1=정답 이유만 / 2=오답 각각 "왜 틀렸는지 + **어떤 상황이면 정답이 됐을지**"까지 (오답의 조건화가 서비스 선택 판단력을 만든다)
- **L3 구체 예시 결합**: 0=서술만 / 1=예시가 개념과 분리(끝에 몰림) / 2=개념 직후 CLI·정책 JSON·시나리오, 예시 형태가 실전 지문과 닮음
- **L4 인지부하**: 0=블록에 신규 용어 8개↑ 정의 없이 / 1=5~7개 또는 일부 미정의 / 2=3~5개, 신규 용어 첫 등장 시 정의
- **L5 시험 무관 분량**: **근거는 감이 아니라 축2 리포트의 「범위 이탈」.** 이탈 10% 초과=0 / 경미=1 / 없음=2
- **L6 선행 지식 연결**: 0=없음 / 1="앞서 배운 대로" 식 모호 / 2=챕터·개념 지목("0-2장의 신뢰 정책이 여기서 Lambda 실행 역할의 AssumeRole로 적용")
- **L7 난이도 분포**: 정의 직문/시나리오 판단/범위 밖 트리비아로 분류. 0=직문 50%↑ 또는 트리비아 존재 / 1=시나리오 50~70% / 2=시나리오 70%↑·직문 20%↓·트리비아 0
- **L8 누적 복습**: 0=종합 퀴즈가 자기 챕터만 / 1=이전 챕터 산발(10%↓) / 2=20~30%가 이전 챕터 결합 문항(예: DynamoDB 챕터에 "이 테이블 접근 IAM 정책" 문항)
- 항목 총량은 8개 유지. 추가 필요 시 통합 우선

### 스키마 피드백 (레거시 전용)
학습 설계 관점 제안을 `docs/SCHEMA_FEEDBACK_AXIS1.md`에 기록 (예: "해설을 '정답 근거'와 '오답별 조건' 필드로 분리하면 L2가 스키마 수준에서 강제된다"). 직접 수정 금지.

### 판정·리포트
통과(유효 총점 85%↑) / 수정(60~85%) / 재구성(60%↓ — 사실은 맞으나 설계 부실). 수정 지시는 실행 가능하게: "해설 보강"(X) → "L2 위반: 3번 문항 해설에 B가 오답인 이유 없음 → 'B(SNS)는 큐잉이 없어 소비자 오프라인 시 유실 — 이 시나리오 부적합' 한 문장 추가"(O).
`reports/axis1/{id}.md`:
```
# 축1 리포트: {id}
모드 / 평가 범위: 전체|부분 평가(N/A: …) / 판정 (총점 n/유효 만점 m)
## 채점표 | 항목 | 점수 | 근거(구체 위치 인용) |
## 수정 지시
## 보충 생성 목록 (결손 성분)
## 반복 약점 메모 (여러 파일 반복 감점 → 생성 프롬프트 개선용)

```
