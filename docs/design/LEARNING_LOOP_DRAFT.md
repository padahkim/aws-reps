## §1 오답 재출제 정책 — 간격 반복

### 1-1. 후보 비교와 선택 (→ D1)

| 후보 | 효과 (간격 반복 관점) | 구현 난도 (1인 프로젝트) | 판단 |
|---|---|---|---|
| 고정 간격 (오답 후 1일/3일/7일 일괄) | 간격은 있으나 **적응 없음** — 계속 틀리는 문항도 같은 스케줄로 흘러가 약점에 노출이 집중되지 않음 | 최소 (타임스탬프 1개) | 효과 손실 대비 절약이 작음 |
| **Leitner 상자식 (상자 3개)** | 맞히면 승급·틀리면 상자 1로 — **틀릴수록 자주, 맞힐수록 드물게**. 간격 반복의 핵심 효과를 정수만 남기고 확보 | 낮음 (문항당 상태 = 상자 번호 1개 + due 시각 1개) | **권고** |
| SM-2 계열 (ease factor, 문항별 부동소수 간격) | 장기(수개월~수년) 기억 유지에 최적화. 시험일이 상한인 이 프로젝트에선 초과 성능 | 높음 — 품질 자기평가(0~5) 입력이 필요한데 4지선다 채점은 이진(정/오)이라 입력 자체가 안 맞음 | 과설계 |

**권고: Leitner 상자 3개.** 근거: ① 시험 준비 지평(수 주~수 개월)에서는 1일→3일→7일 3단계로 간격 효과가 충분히 소진된다 — 그 이상의 간격은 시험일을 넘긴다. ② 상태가 문항당 정수 1개(+due 시각)라 localStorage·마이그레이션·디버깅 전부 단순하다. ③ RUBRIC §8이 요구하는 학습과학 원리(인출 연습 + 간격)를 앱 수준에서 구현하는 최소 기계다 — L8(누적 복습)이 콘텐츠 수준에서 하는 일을 오답 노트가 런타임에 이어받는다.

> **Leitner 상자란**: 원래 종이 플래시카드를 물리적 상자 여러 개에 나눠 담는 공부법이다 — 맞힌 카드는 다음 상자로 옮겨 덜 자주 보고, 틀린 카드는 상자 1로 되돌려 매일 본다. 이 앱에서 "상자"는 실물이 아니라 **문항마다 붙는 1~3 상태값**(localStorage의 `box` 필드)이고, 효과는 "모르는 문제일수록 자주, 아는 문제일수록 뜸하게"가 자동으로 굴러가는 것이다.

### 1-2. 상자·간격 정의

```
상자 1 (약점):  간격 1일
상자 2 (학습중): 간격 3일
상자 3 (안정):  간격 7일  → 여기서 정답이면 졸업(숙달, §2-1)
```

- **진입**: 어떤 문항이든 **오답이 발생한 순간** 상자 1로 진입, `dueAt = 오답 시각 + 1일`. 처음부터 맞힌 문항은 이 시스템에 아예 들어오지 않는다(오답 노트 = 이름 그대로 오답만).
- **승급**: due가 된 문항을 맞히면 한 칸 승급, `dueAt = 정답 시각 + 승급한 상자의 간격`.
- **강등**: 어디서든(오답 노트든 챕터 재응시든) 틀리면 상자 1로 복귀, `dueAt = +1일`. 졸업했던 문항도 다시 틀리면 상자 1로 재진입한다 — 이것이 망각 반영의 전부다(별도 망각 곡선 계산 없음).
- **조기 정답 (→ D2)**: `dueAt` 이전의 정답은 **승급시키지 않는다** (오답은 언제든 강등). 근거: 방금 해설을 읽고 몇 분 뒤 맞힌 것은 단기 기억 재인이지 간격을 둔 인출이 아니다 — 이 한 줄이 없으면 사용자가 같은 자리에서 연타해 상자를 통과할 수 있어 간격 반복이 무력화된다. 챕터 안에서의 즉시 재도전 자체는 막지 않는다(교정 효과가 있으므로) — 기록만 하고 승급에 안 쓴다.

### 1-3. "다시 풀 시간이 됐다"의 노출

1. **오답 노트 진입 시 정렬**: due 문항(현재 시각 ≥ dueAt)을 최상단에, dueAt 오래된 순(연체 우선) → 같으면 상자 낮은 순(약점 우선). 아직 due가 아닌 문항은 접힌 영역("예정")에.
2. **due 카운트 배지**: 내비게이션의 오답 노트 항목과 대시보드에 "복습 N" 숫자만. 알림·푸시 없음 — localStorage 앱의 분수를 지킨다.
3. 그 외 노출 장치(리마인더, 스트릭, 데일리 목표)는 MVP 미포함 — 지표·장치 과잉 금지.

### 1-4. 재출제 시 정답 처리와 셔플 (→ D2, D3)

- **정답 처리 정의**: 오답 노트에서 due 문항을 맞히면 승급(§1-2). 채점은 챕터 내 `<Quiz>`와 동일 로직(복수 정답은 완전 일치만 정답 — answer[] 배열 전체 일치).
- **선택지 셔플 (권고: 항상 셔플)**: 재출제에서 같은 자리의 답을 고르는 위치 기억을 차단하기 위해 매 출제마다 choices를 섞는다(첫 출제 포함 — 일관성). answer는 인덱스 참조이므로 렌더 시 매핑만 하면 되고 저장 구조에는 영향 없다. 예외: 선택지가 순서를 참조하는 문항("A와 B 모두" 류)은 셔플이 깨뜨린다 — 규약 v1에 `fixedChoiceOrder?: boolean`을 optional 후보로 예약할 것을 제안(레거시에 해당 유형이 실존하는지는 표준화 세션이 확인).

## §2 숙달 판정 기준

### 2-1. 문항 단위 — 상태 5종이 전부

```
미시도 → (첫 시도 정답) → 숙달
       → (첫 시도 오답) → 상자1 ⇄ 상자2 ⇄ 상자3 → (상자3에서 due 정답) → 숙달
숙달 → (재실패) → 상자1
```

**숙달의 정의: 첫 시도 정답, 또는 Leitner 졸업(상자 3에서 due 상태의 정답).**

- 대안 "연속 정답 n회"를 채택하지 않는 근거: 간격 없는 연속 정답은 단기 기억 측정이다. Leitner 졸업이 곧 "1일·3일·7일 간격을 둔 연속 정답 3회"이므로, 연속성 기준은 상자 시스템 안에 이미 들어 있다 — 별도 카운터는 이중 장부.
- 대안 "마지막 시도 기준"을 채택하지 않는 근거: 오답 직후 즉시 재도전 정답(§1-2 조기 정답)이 숙달로 잡혀 기준이 물러진다.
- 첫 시도 정답을 1회로 숙달 인정하는 근거: 전 문항을 상자에 태우면 복습 큐가 문항 수 전체로 불어나 due가 인플레이션된다. 시험이 종점인 앱에서 복습 자원은 **틀린 적 있는 문항**에 집중하는 것이 옳고, 첫 정답 문항이 실은 요행이었다면 챕터 재응시·finalQuiz에서 틀리는 순간 상자 1로 들어온다(자기 교정).

### 2-2. 개념 단위 — 약점 개념 산출

- **산식**: concept 태그별로, 시도된 문항의 **최근 시도 기준** 정답률 = (마지막 시도가 정답인 문항 수) ÷ (시도된 문항 수). 생애 누적 정답률을 쓰지 않는 근거: 학습 초기의 오답이 영구히 분모를 오염시켜 "약점 극복"이 지표에 안 보인다.
- **약점 판정**: 정답률 < 70% **이고** 시도 문항 ≥ 2인 concept. (문항 1개짜리 concept은 표본이 아니라 소음 — 판정 유보.)
- **폴백 (concept 태그 없는 레거시 문항)**: 전역 키의 접두가 곧 챕터 id이므로, concept이 없으면 **챕터 id를 유사 concept으로 귀속**한다. 표시도 "Lambda(챕터)" 식으로 출처를 구분. 태그가 표준화 단계에서 채워지면 자동으로 세분화된다 — 저장 구조 변경 없음(§4-2: concept은 저장하지 않고 런타임 조인).
- concept은 규약 v1에서 배열(`concept: string[]`, PREWORK §2-4)이 될 수 있다 — 배열이면 문항 결과를 각 concept에 중복 귀속(교차 챕터 결합 문항이 두 개념 모두의 신호가 되는 것이 L8의 취지와 정합).

### 2-3. 챕터 단위 — "완료" 배지의 조건식

```
완료(ch) ⇔ 열람(ch.visitedAt 존재)
         ∧ finalQ(ch) ≠ ∅ 인 경우:
             finalQ 전 문항 시도됨
             ∧ (마지막 시도가 정답인 finalQ 문항 비율) ≥ 80%     ← D7
```

- `finalQ(ch)` = 해당 챕터 quiz 중 `scope === "final"` 문항. 판정 기준을 **마지막 시도**로 두는 이유: 숙달(졸업) 기준으로 걸면 오답 1개가 배지를 최소 11일(1+3+7) 지연시켜 진도 동기를 죽인다. 틀렸던 문항의 장기 정착은 배지와 무관하게 복습 루프가 따로 책임진다(§2-4).
- 열람의 정의는 MVP에서 "챕터 페이지 방문"이다. 섹션 단위 열람 추적은 본문이 자유 jsx라 셸이 신뢰성 있게 관측할 수 없음 — 규약 v1에 섹션 개념이 생기면 후속 강화(§4-1의 유보 필드).
- **finalQ = ∅ 인 챕터 (→ D4)**: 레거시 7파일 중 5파일이 퀴즈 성분 X(PREWORK §1)이므로 예외가 아니라 다수 케이스다. 권고: 열람만으로 완료 처리하되 배지를 **"열람 완료"로 구분 표기**(정식 "완료"와 시각 구분). 완료 불가로 두면 진행률(§3)이 표준화 완료 전까지 영구히 눌린다.

### 2-4. 망각 반영 — 배지와 복습 루프의 분리 (→ D5)

- **due 문항은 챕터 완료 여부와 무관하게 계속 뜬다.** 완료는 "본편을 마쳤다"는 스냅샷이고, 복습 루프는 문항 단위로 독립해서 돈다(§1-2 강등 규칙이 졸업 문항에도 적용되므로 망각은 재실패 시 자동 포착).
- **배지 정책 권고: 완료 배지는 유지하고, due 존재는 배지 옆 보조 표기("복습 n")로만 노출.** 대안(배지를 "복습 필요"로 강등)은 진행률이 오르락내리락해 완주 동기를 해친다 — 시험 준비생 1명에게 필요한 것은 정확한 형벌이 아니라 "본편은 끝냈고, 복습이 n개 남았다"는 두 사실의 병렬 표시다.

## §3 진도·커버리지 계산식

### 3-1. 전체 진행률 (→ D6)

```
전체 진행률 = 완료 챕터 수(§2-3, "열람 완료" 포함) ÷ 레지스트리의 전체 챕터 수
```

**권고: 도메인 비중 무가중.** 근거: ① 가중 진행률은 직관을 배반한다("20챕터 중 10개 끝냈는데 43%"). ② 시험 비중 정보는 §3-2 도메인 커버리지가 전담한다 — 진행률에도 섞으면 같은 정보의 이중 계상. ③ 챕터 분량 자체가 이미 도메인 비중을 반영해 설계되어 있다(CURRICULUM §2: Domain 1이 챕터 9개로 최다) — 챕터 수 균등 분할이 사실상의 근사 가중이다.

### 3-2. 도메인별 커버리지

```
커버리지(domain d) = 완료 챕터 수(d) ÷ 전체 챕터 수(d)      — 표시: 시험 비중과 병렬
  예: "Domain 1 · 개발 (시험 32%) ████████░░ 78%"
```

- 챕터→도메인 귀속은 `meta.domain`으로 런타임 조인(저장 안 함 — §4-2). 0단계(기반) 챕터처럼 도메인 귀속이 애매한 것은 meta에 적힌 값을 그대로 따른다 — 학습 루프가 재분류하지 않는다.
- 산식을 "숙달 문항 비율"이 아니라 챕터 완료 기반으로 두는 근거: 레거시 다수가 퀴즈 성분 X라 문항 기반 커버리지는 표준화 완료 전까지 왜곡된다. 챕터 완료(§2-3)가 이미 finalQuiz 점수를 내포하므로 정보 손실도 작다.

### 3-3. 대시보드 지표 — 3개로 고정 (지표 과잉 금지)

| # | 지표 | 산식 출처 | 존재 이유 |
|---|---|---|---|
| 1 | 전체 진행률 | §3-1 | "얼마나 왔나" — 완주 동기 |
| 2 | 오늘의 복습 (due 문항 수) | §1-3 | "지금 뭘 해야 하나" — 유일한 행동 유도 지표 |
| 3 | 도메인 커버리지 (4-bar) | §3-2 | "시험 비중 대비 구멍이 어디인가" |

- 약점 개념 Top N(§2-2)은 대시보드가 아니라 **오답 노트 화면 소속**이다 — 대시보드는 "다음 행동" 결정용 3개로 끝내고, 진단 상세는 행동하러 들어간 화면에서 보여준다.
- 정답률 추이, 학습 시간, 스트릭 등은 MVP 미포함.

## §4 데이터 구조 초안 (localStorage) — APP_ARCHITECTURE_DRAFT §3의 델타

### 4-1. 키 구조

APP_ARCHITECTURE_DRAFT §3의 2키 체계(`dva.progress.v1` / `dva.review.v1`)를 유지한다. `gk` = 전역 문항 키 `"{chapterId}:{안정 문항 id}"` (어댑터 합성, 규약 무변경 — PREWORK §2-4; 식별자 규칙은 §4-2 각주의 정정 참조).

**`dva.progress.v1`의 필드 목록은 이 문서가 소유하지 않는다 — 정본은 코드다** [#207, 2026-08-03]: `lib/progress/records.ts`의 `Progress`(키 전체) · `QuestionRecord`(문항) · `ChapterRecord`(챕터)가 구조를 소유하고, 이 키의 쓰기는 전부 그 파일을 거친다. 처음 여기 있던 필드 목록은 코드가 생기는 순간 사본이 됐고 실제로 낡았다(정정 이력의 3건이 전부 이 절에서 났다) — 필드를 문서가 소유하지 않으면 낡을 게 없다. 문서가 지키는 것은 "왜 이 필드들인가"다:

- **저장은 사실만** — 문항의 시도·정오·시각, 챕터의 열람·완료 스냅샷. 약점 개념(§2-2)·커버리지(§3-2)·due 카운트처럼 파생 가능한 값은 저장하지 않는다: 전부 두 키 + 콘텐츠 데이터의 런타임 조인으로 계산한다.
- **쓰기는 전부 한 모듈을 경유한다** — 구조 버전·read-repair(§4-3)·필드 불변식을 지키는 코드가 한 곳에 모여야 마이그레이션이 가능하다.

**`dva.review.v1`은 아직 구현이 없다** — 오답 노트 착수(#86 잔여) 때 만들어지며, **구현 시 필드 목록의 정본을 progress와 같이 코드로 이관한다**. 그때까지의 초안:

```ts
"dva.review.v1": {                         // [교체] 초안의 {addedAt, clearedAt?} → Leitner 상태로
  v: 1,
  items: { [gk]: {
    box: 1 | 2 | 3,                        // 현재 상자 (§1-2)
    dueAt: string,                         // 다음 재출제 시각 = 마지막 채점 + 상자 간격
    graduatedAt?: string,                  // 존재하면 졸업(숙달) — due 계산에서 제외.
  }},                                      //   재실패 시 이 필드를 지우고 box=1로 (§1-2 강등)
}
```

- 초안의 `addedAt`/`clearedAt`은 폐기: 진입 이력은 `questions[gk]`의 시도 기록으로 복원 가능하고, cleared 의미는 `graduatedAt`이 정확히 대체한다. 오답 노트 목록 = `items`에서 `graduatedAt` 없는 것, due 목록 = 그중 `dueAt ≤ now`.

### 4-1a. `firstResult` — 구현 시 추가된 필드 [사용자 결정, 2026-08-02 · #66/PR #202]

**§2-1이 숙달을 "첫 시도 정답"으로 정의하는데, `QuestionRecord`의 기본 네 필드(`attempts`·`correct`·`lastResult`·`lastAt`)로는 그 사실이 재응시 한 번에 사라진다.** `attempts ≥ 2`가 되는 순간 첫 시도가 정답이었는지 복원할 방법이 없고, 이 절이 "파생 가능한 값은 저장하지 않는다"고 한 것과 달리 **이건 파생되지 않는다**. 판정을 실제로 만드는 것은 오답 노트 착수(#86 잔여) 때지만 데이터는 첫 쓰기 경로가 착지하는 순간부터 쌓이므로, 그때 가서 소급할 수 없다는 비대칭 때문에 필드만 먼저 넣는다.

- 첫 채점에만 쓰이고 그 뒤로는 고정. 읽는 코드는 아직 없다.
- optional인 이유는 이 필드 이전에 저장된 기록 때문이다 — read-repair가 `attempts === 1`인 기록에 한해 `lastResult`로 복원하고(그 경우 첫 결과 = 마지막 결과), 2회 이상이면 근거가 없어 비워 둔다.
- 쓰기 모듈의 경로: 구현체는 `lib/progress/records.ts`다(§4-1). 초안과 이 문서가 적었던 `store.ts` 는 **버렸다** [2026-08-02, PR #202]: Next/React 리포에서 `store` 는 Redux·Zustand 류 메모리 상태 컨테이너로 읽히는데, 이 파일은 localStorage 저장소이면서 훅(`useQuestionRecords`)까지 export 해 이름과 API 표면이 함께 오독을 부른다. 경로 이름은 이 문서가 지킬 결정이 아니므로 코드 쪽 가독성을 따랐다.

### 4-2. 규약 의존 지점 명세 — 이 표 밖의 의존은 금지

| 의존 지점 | 소비하는 규약 요소 | 저장 여부 | 규약 v1 변경 시 영향 |
|---|---|---|---|
| 문항 식별 | `meta.id` + `quiz[].slug ?? quiz[].id` (gk 합성) | **저장함** (유일한 하드 의존) | id 개명 = 진도 마이그레이션 필요. v1에 챕터 id 안정성 요구 이미 등재(ARCHITECTURE §5-①) |
| 챕터 완료 | `quiz[].scope === "final"` | 저장 안 함 | 어휘 변경 시 어댑터 필터 1줄 |
| 약점 개념 | `quiz[].concept` (없으면 챕터 id 폴백 §2-2) | 저장 안 함 | 단수→배열 등 어떤 변경도 런타임 조인이라 저장 무영향 |
| 커버리지 | `meta.domain` | 저장 안 함 | 동상 |
| 셔플 | `choices` 배열 + `answer` 인덱스 (+ 후보 `fixedChoiceOrder?`) | 저장 안 함 | 렌더 시 매핑뿐 |

즉 규약이 v1에서 어떻게 바뀌어도 **저장 데이터가 깨지는 경로는 문항 식별자 개명 하나**다. 문항에 "안정 식별자·정답·해설이 있다"는 가정만 성립하면 이 설계는 유효하다.

> **문항 식별자를 `id` → `slug ?? id`로 정정 [사용자 결정, 2026-08-02 · #66/PR #202].** 이 문서(2026-07-13)는 gk를 `quiz[].id`로 적었는데, 그 뒤 **#69에서 `id`가 안정 식별자가 아님이 확정됐다** — `content/chapters/*/drills.ts`는 생성물이고 `scripts/import-drills.ts`가 `id`를 `q${i+1}`로 위치에 따라 발급하므로, 원본 JSON에 문항 하나가 끼어들면 그 뒤 id가 전부 밀린다. 그래서 리포는 이미 문항 **선별**에 `slug`를 쓰고 있었고(`content/schema.ts` Question.slug), 진도 키만 옛 규칙에 남아 있었다. 여기 적힌 "id 개명 = 마이그레이션 필요"는 개명을 **알아챌 수 있는** 사건으로 전제하는데, 위치 밀림은 화면에 아무 흔적을 남기지 않아 그 전제부터 성립하지 않는다. `slug`가 없는 손작성 문항은 `id`로 폴백한다(생성물이 아니라 위치 발급 자체가 없다). 유일성은 검증기가 **해석된 키**에서 강제한다(`QUESTION_KEY_DUP`).

### 4-3. 마이그레이션

- 키 접미(`.v1`)가 메이저(비호환) 버전, 내부 `v` 필드가 마이너(호환 확장) 버전. 로드 시 `v`를 보고 read-repair(누락 필드 기본값 주입) — 마이그레이션 코드는 쓰기 모듈(`lib/progress/records.ts`, §4-1) 한 곳에만.
- 알 수 없는 필드는 보존한 채 통과시킨다(향후 필드 추가가 구버전 세션에서 지워지지 않도록).
